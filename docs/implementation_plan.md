# Digital Art Store — Detailed Implementation Plan

> Companion to [digital_art_store_development_plan.md](./digital_art_store_development_plan.md).
> That document defines **what** the platform is. This one defines **how it gets built**:
> schema, services, endpoints, file layout, sequencing and acceptance criteria.

**Guiding constraint for every decision below:**

> Simple for the customer. Simple for the administrator. Secure by design. Fast by default.
> No unnecessary WordPress/WooCommerce complexity.

Where a choice exists, this plan picks the option that requires the **administrator to understand
less** and the **server to do less work per request**.

| Admin | **Filament 5.10** | Delivers the "WooCommerce admin" in days, not months: resources, tables, forms, actions, MFA. |

| Storage | Flysystem: `public` (CDN assets), `private` (sellable files), `backups` | Driver-swappable: local disk in dev, S3-compatible in production, identical code. |
| Email | SMTP configured **in the admin UI**, not only `.env` | See §15. |

| Tests | **Pest 4** | Readable feature tests; the money paths in §21 are non-negotiable. |

### 1.1 Dependencies we deliberately do **not** take

- **No ecommerce package** (Bagisto / Lunar / Aimeos). Each brings a catalog, tax, shipping and
  variant model sized for physical multi-vendor retail. We sell files. Their model would be a tax
  on every future change, not a gift.
- **No `paypal/paypal-checkout-sdk`.** It has gone through long unmaintained stretches
  **[VERIFY current status]**. The REST API is stable, well documented, and ~8 endpoints wide for
  our purposes. We call it directly (§6.3).
- **No Inertia / Vue / React on the storefront.** Server-rendered HTML *is* the SEO requirement
  from the source plan, and it is the shortest path to good Core Web Vitals.

## 3. Configuration model — "paste the keys and it works"

This section decides whether the administrator experience succeeds or fails.

### 3.1 Why `.env`-only configuration is not acceptable

WooCommerce's real strength is not its code — it is that the shop owner pastes two strings into a
form, clicks *Save*, and payments work. They never open a terminal. We must match that, and `.env`
cannot: editing it requires SSH access, a file edit, and a `config:cache` rebuild.

### 3.2 Three-tier settings resolution

Every setting resolves in this order; first hit wins:

```
1. Database `settings` table   (edited in the admin UI)   ← the owner's lane
2. Environment variable        (.env)                     ← the developer's lane
3. config/*.php default
```

`SettingsRepository` is the single accessor:

```php
Settings::get('paypal.live.client_id');          // decrypts transparently
Settings::set('paypal.live.client_id', $value);  // encrypts if registered as secret
Settings::forgetCache();
```

- The whole settings map is cached in Redis under one key (`settings:v1`) as a single array: one
  Redis read per request, invalidated on any write. No N+1 setting lookups.
- Keys are declared in a `SettingDefinition` registry — `key`, `type`, `secret` (bool), `group`,
  `validation`, `default`. The registry drives both the Filament form *and* validation, so adding
  a setting means editing one file.
- `secret: true` values are stored via `Crypt::encryptString()` (AES-256 authenticated, keyed on
  `APP_KEY`) and are never rendered back to the browser in full. The form displays a masked value
  (`••••••••1a2b`) and only overwrites when something new is typed.

### 3.3 First-run setup wizard

Route `/setup`, guarded by `EnsureSetupComplete` middleware, which redirects **to** `/setup` while
`settings.setup_completed` is false and returns 404 for the route afterwards.

```
Step 1  System check    PHP version, extensions (vips/imagick, intl, zip, bcmath), writable
                        storage, Redis reachable, DB reachable, queue worker alive.
                        Red/green checklist. Cannot continue until all green.
Step 2  Store identity  Store name, legal name, support email, currency, timezone, logo.
Step 3  Admin account   Email, strong password, enforced 2FA enrolment (QR + recovery codes).
Step 4  Payments        PayPal mode (Sandbox/Live), Client ID, Secret.
                        [ Test connection ]  → live OAuth probe; green check or precise error.
                        [ Enable payments ] → auto-registers the webhook (§6.6).
Step 5  Email           SMTP host/port/user/pass/encryption.
                        [ Send test email ] → to the admin address.
Step 6  Done            Links: create first product / view storefront / dashboard.
```

Steps 4 and 5 are **skippable**: the store can be configured and products created before payments
go live. The storefront then renders checkout as disabled, and the dashboard carries a persistent
"Payments not configured" banner with a one-click link back to the payments settings.

The wizard writes to `settings`, never to `.env`.

### 3.4 `config/paypal.php` (env fallback only)

```php
return [
    'mode'       => env('PAYPAL_MODE', 'sandbox'),   // sandbox|live
    'endpoints'  => [
        'sandbox' => 'https://api-m.sandbox.paypal.com',
        'live'    => 'https://api-m.paypal.com',
    ],
    'sandbox' => [
        'client_id'     => env('PAYPAL_SANDBOX_CLIENT_ID'),
        'client_secret' => env('PAYPAL_SANDBOX_CLIENT_SECRET'),
        'webhook_id'    => env('PAYPAL_SANDBOX_WEBHOOK_ID'),
    ],
    'live' => [
        'client_id'     => env('PAYPAL_LIVE_CLIENT_ID'),
        'client_secret' => env('PAYPAL_LIVE_CLIENT_SECRET'),
        'webhook_id'    => env('PAYPAL_LIVE_WEBHOOK_ID'),
    ],
    'timeout'    => 15,
    'retries'    => 3,
    'brand_name' => env('PAYPAL_BRAND_NAME'),
];
```

Sandbox and live credentials live under **separate keys** so that flipping the mode toggle never
destroys the other environment's keys, and so a mis-set toggle can never attempt a real charge
with test credentials or the reverse.

## 4. Database schema

Conventions: `id` BIGINT unsigned PK; `uuid` CHAR(36) wherever an identifier is exposed publicly;
money as **integer minor units** (`INT UNSIGNED` cents) plus `currency` CHAR(3) — never
`FLOAT`/`DOUBLE`; all timestamps UTC; soft deletes only where an audit trail needs the row.

### 4.1 Catalog

| type | enum | `single`, `mini_set`, `collection`, `bundle` |
| title | varchar(255) | |
| slug | varchar(255) unique | indexed |
| subtitle | varchar(255) null | editorial line used on cards |
| description | mediumtext null | sanitised HTML (§16.6) |
| price_cents | int unsigned | |
| sale_price_cents | int unsigned null | |
| sale_starts_at / sale_ends_at | timestamp null | scheduled promotions |
| currency | char(3) | default `USD` |

| file_count | smallint unsigned | denormalised for cards |

Indexes: `(status, published_at)`, `(type, status)`, `slug`, and FULLTEXT `(title, subtitle,
description)` for internal search.

**`product_files`** — the sellable payload. Private storage only.

```
id, product_id FK, disk ('private'), path, original_filename, display_name,
mime_type, size_bytes, checksum_sha256, format enum(pdf|jpg|png|svg|zip),
ratio varchar null, print_size varchar null, dpi smallint null,
width_px/height_px int null, position, created_at
```

Index `(product_id, position)`. Unique `(product_id, checksum_sha256)` prevents accidental
double-upload of the same file.

**`product_images`** — public previews. Never the sellable file.

```
id, product_id FK, disk ('public'), path_original, alt_text varchar(255) null,
width, height, dominant_color char(7), blurhash varchar(64) null,
is_cover bool, is_mockup bool, watermarked bool, position, variants json, timestamps
```

`variants` holds the generated derivative map (§10.2) so the Blade image component can build a
`srcset` without touching the filesystem:

```json
{"webp": {"320": "...", "640": "...", "960": "...", "1280": "...", "1920": "..."},
 "avif": {"320": "...", "640": "...", "960": "...", "1280": "...", "1920": "..."}}
```

**`collections`**

```
id, uuid, title, slug unique, description text null, cover_image_id null,
type enum(manual|smart), rules json null, status enum,
is_indexable bool default false, min_products_for_index smallint default 4,
position, published_at, timestamps
```

`is_indexable` implements the source plan's rule that a collection only earns a crawlable page once
it holds enough content. A scheduled job flips it (§11.5).

**`collection_product`** — `collection_id, product_id, position`; PK `(collection_id, product_id)`.

**`attributes` / `attribute_values` / `product_attribute_value`** — one generic taxonomy covering
Style, Room, Theme, Subject, Ratio and Colour, instead of six bespoke columns. It also makes the
faceted-but-noindex browsing in §11.5 trivial.

```
attributes:       id, key unique (style|room|theme|subject|ratio|color), label,
                  is_filterable bool, is_seo_landing bool
attribute_values: id, attribute_id FK, value, slug, label, position
                  unique (attribute_id, slug)
```

**`bundle_items`** — `bundle_product_id FK, child_product_id FK, position`.
A bundle delivers the union of its children's `product_files`. Files are **never duplicated on
disk**; §8.3 explains how grants fan out.

### 4.2 Orders, payments, customers

**`customers`**

```
id, uuid, email_encrypted text, email_hash char(64) unique, email_domain varchar(64),
name_encrypted text null, locale char(5) default 'en', country char(2) null, marketing_consent bool,
first_order_at, last_order_at, orders_count, lifetime_value_cents, timestamps
```

- `email_hash` = `hash_hmac('sha256', strtolower(trim($email)), BLIND_INDEX_KEY)`. It is the only
  way to look a customer up. See §9.
- `email_domain` is kept in clear text deliberately: it enables abuse analytics (a burst of orders
  from one throwaway domain) without exposing any individual.
- No password column in MVP — the store is guest-checkout only. If accounts arrive later they live
  in `users` with Argon2id, never here.

**`orders`**

```
id, uuid, number varchar(16) unique, customer_id FK, status enum, currency,
subtotal_cents, discount_cents, tax_cents, total_cents,
coupon_id null, coupon_code varchar(64) null,
email_hash char(64), ip_hash char(64) null, user_agent_hash char(64) null,
placed_at, paid_at, completed_at, cancelled_at, refunded_at,
manual_review_reason varchar(255) null, admin_notes text null, metadata json,
terms_version varchar(16), terms_accepted_at timestamp, terms_accepted_ip_hash char(64),
locale char(5) default 'en', is_free bool default false, timestamps
```

`terms_version` records **which revision** of the terms the customer accepted, not merely that
they ticked a box. A policy that changed after the sale is not the policy the customer agreed to,
and in a dispute the only useful evidence is the exact text in force at that moment (§7.7).

`number` is human-facing (`MA-1048`), drawn from a dedicated sequence — never the autoincrement id,
which would leak total order volume. Indexes: `(status, created_at)`, `customer_id`, `email_hash`,
`number`.

**`order_items`** — a **price snapshot**, immutable after creation.

```
id, order_id FK, product_id FK (nullable on product delete), product_type,
title_snapshot, slug_snapshot, unit_price_cents, quantity, discount_cents, total_cents,
file_manifest json, created_at
```

`file_manifest` freezes which `product_file` ids were sold, so later edits to a product never alter
what a past customer is entitled to.

**`payments`**

```
id, uuid, order_id FK, provider enum(paypal), mode enum(sandbox|live),
provider_order_id varchar(64), provider_capture_id varchar(64) null,
status enum, amount_cents, currency, fee_cents null, net_cents null,
payer_email_hash null, payer_id varchar(64) null, raw_response json,
verified_at, failure_code varchar(64) null, failure_message text null, timestamps
```

Unique indexes on `(provider, provider_capture_id)` and `(provider, provider_order_id)`. These two
constraints are the **database-level** guarantee that a replayed webhook cannot create a second
payment (§6.7). Application logic can have bugs; a unique index cannot.

**`webhook_events`** — the idempotency ledger.

```
id, provider, event_id varchar(64) UNIQUE, event_type varchar(64),
resource_type varchar(64), resource_id varchar(64) null,
signature_verified bool, payload json,
status enum(received|processed|failed|ignored), attempts tinyint,
processed_at, error text null, received_at
```

Unique on `event_id` — the insert itself acts as the lock.

**`refunds`** — `id, payment_id FK, provider_refund_id unique, amount_cents, reason, status,
initiated_by_user_id, raw_response json, timestamps`.

### 4.7 Internationalisation — English and Spanish

The store ships bilingual from day one. This is not a feature bolted on later: it determines the
schema, the URL structure, the SEO markup and the email pipeline, and retrofitting it after launch
means re-slugging a live catalog and losing accumulated search ranking.

#### 4.7.1 Translation storage — tables, not JSON columns

Two approaches exist. We take the second.

| | JSON column `{"en": "...", "es": "..."}` | Translation table |
|---|---|---|
| Lookup by slug | Awkward, unindexable | Indexed, unique per locale |
| FULLTEXT search per language | Impossible | Native |
| Per-locale publication status | Clumsy | Natural |
| Schema complexity | Lower | One extra table per entity |

Slug lookup happens on **every product page request** and must hit an index, and search quality
depends on per-language FULLTEXT. A JSON column breaks both. The extra table is worth it.

**`product_translations`**

```
id, product_id FK, locale char(5),
title varchar(255), subtitle varchar(255) null, description mediumtext null,
slug varchar(255),
status enum(draft|published) default draft,
is_machine_translated bool default false, reviewed_at timestamp null,
timestamps

unique (product_id, locale)
unique (locale, slug)          ← the critical one
index  (locale, status)
FULLTEXT (title, subtitle, description)
```

`unique (locale, slug)` rather than a globally unique slug: the same artwork can be
`/en/art/coffee-bar-wall-art` and `/es/arte/arte-mural-para-bar-de-cafe`, and two unrelated products
may legitimately share a slug across different languages.

**`collection_translations`** — `collection_id, locale, title, description, slug, status`; same
constraints.

**`attribute_value_translations`** — `attribute_value_id, locale, label, slug`. Style, room and
theme names are customer-visible and appear in URLs.

**`product_images.alt_text`** becomes a JSON column `{"en": "...", "es": "..."}`. Alt text is never
searched or used for lookup, so the table overhead buys nothing here. This is the one place the JSON
approach is correct.

**`seo_metadata`** gains a `locale` column; the unique key becomes
`(seoable_type, seoable_id, locale)`. Each language needs its own title, description and OG image.

**`legal_documents`** and **`legal_document_versions`** — new tables (§7.7.2 needs versioning, this
adds language):

```
legal_documents:          id, key (terms|privacy|refunds|ai_disclosure|licence), current_version_id
legal_document_versions:  id, legal_document_id FK, version varchar(16),
                          effective_at, published_at, created_by_user_id, timestamps
legal_document_bodies:    id, version_id FK, locale char(5), title, body_html, timestamps
                          unique (version_id, locale)
```

A version carries **both languages together**, so publishing a terms update never leaves one locale
on stale text. `orders.terms_version` keeps pointing at the version; a new `orders.locale` column
records which language that customer actually read, so "what did this buyer agree to" stays
answerable in a dispute.

#### 4.7.2 Per-locale publication

`product_translations.status` means a product can be live in English while its Spanish translation
is still a draft.

**A product missing a published translation does not appear in that locale's catalog at all.** It is
excluded from listings, search and the sitemap for that language. The alternative — falling back to
English inside the Spanish storefront — produces a catalog in mixed languages, which reads as
careless to customers and registers as thin or duplicated content to search engines. Absence is
better than a half-translated page.

The admin surfaces this plainly: the product list has a locale column showing `EN ✓ · ES —`, and a
dashboard tile counts products awaiting translation.

#### 4.7.3 URL structure

```
/                                  → 302 to detected locale, x-default hreflang
/en/                               English home
/en/shop                           catalog
/en/art/{slug}                     product
/en/collections/{slug}             collection
/en/style/{slug}                   attribute landing
/en/terms  /en/privacy             legal

/es/                               Spanish home
/es/tienda                         catalog
/es/arte/{slug}                    product
/es/colecciones/{slug}             collection
/es/estilo/{slug}                  attribute landing
/es/terminos  /es/privacidad       legal
```

Decisions behind this:

- **Subdirectories, not subdomains or ccTLDs.** One domain accumulates all the ranking authority,
  there is nothing extra to buy or configure, and Google treats the structure as unambiguous.
- **Both locales carry a prefix.** An unprefixed default language creates two URLs for the same
  English page (`/art/x` and `/en/art/x`) and invites duplicate-content handling problems. Prefixing
  both is slightly less pretty and considerably safer.
- **Route segments are translated**, not just slugs. `/es/arte/` reads as a Spanish site;
  `/es/art/` reads as an English site with Spanish text pasted into it, and the segment is a real
  (if minor) relevance signal.
- **`/` redirects, never serves content.** It issues a 302 — not 301 — based on `Accept-Language`,
  with `x-default` hreflang pointing at it. A 301 would permanently cache one visitor's language
  preference in intermediate proxies for everyone.

**Crawlers are never redirected by language detection.** Googlebot requesting `/en/` gets English,
and requesting `/es/` gets Spanish, regardless of any header or cookie. Auto-redirecting a crawler
is the most common way to get half a multilingual site de-indexed.

An explicit choice from the language switcher sets a one-year cookie, which the root redirect
honours ahead of `Accept-Language`. The switcher links to the **equivalent page** in the other
locale — not to the home page — resolving through the translation table and falling back to that
locale's home only when no translation exists.

#### 4.7.4 hreflang and sitemaps

Every page emits reciprocal annotations:

```html
<link rel="alternate" hreflang="en" href="https://moneraart.com/en/art/coffee-bar-wall-art" />
<link rel="alternate" hreflang="es" href="https://moneraart.com/es/arte/arte-mural-bar-de-cafe" />
<link rel="alternate" hreflang="x-default" href="https://moneraart.com/" />
```

Rules: annotations must be **reciprocal** (if EN points to ES, ES must point back, or Google ignores
both), they must use **absolute URLs**, and a page with no published translation in the other locale
emits **no alternate for it** rather than pointing at a fallback.

Canonical URLs are **self-referential per locale**: the Spanish page canonicalises to itself, never
to the English one. Canonicalising a translation to its source tells Google to drop it from the
index entirely — a mistake that silently destroys an entire language's traffic.

Sitemaps split per locale (`/sitemaps/products-en.xml`, `-es.xml`), both listed in the index, each
entry carrying `xhtml:link` alternates.

#### 4.7.5 Translation workflow

The owner writes in one language. The other must not be a blocker.

```
Save product in Spanish
   → queue TranslateProductContent (title, subtitle, description, alt text)
   → write to product_translations(locale: en) with
        is_machine_translated = true, status = draft
   → admin sees "EN translation ready for review" badge
   → admin edits and approves  → is_machine_translated = false, reviewed_at set, status = published
```

Mirrors the SEO automation pattern in §11.1, and for the same reason: **machine output is a draft a
human approves, never something that publishes itself.** Auto-published machine translation at scale
is thin content, and in a product description it will eventually produce something embarrassing in a
language the owner cannot proofread at a glance.

SEO metadata is generated **per locale from that locale's content** (§11.1), never by translating
the English meta description — Spanish search queries are not translated English queries, and a
translated meta description targets the wrong phrases.

Legal documents are **always translated by a human**, and they are not translated at runtime at all.
Each version stores both languages as finished pages (§4.7.1); the site serves whichever the
visitor's locale selects, and the language switcher moves between them. A machine-translated terms
page is not a document anyone should rely on in a dispute.

same voice documented in `legal_content.es.md` §1. DeepL and Google Translate render it accurately
and flatly. An LLM can be handed the voice guide as a system prompt and told to translate the tone
rather than the words. DeepL remains available behind the same interface for anyone who prefers a
dedicated engine, and its free tier covers this volume entirely.

## 5. Domain layer

### 5.1 Order state machine

```
                   ┌──────────────┐
                   │   pending    │  order row created, PayPal order created
                   └──────┬───────┘
          capture fails   │   capture succeeds
        ┌─────────────────┼─────────────────┐
        ▼                 ▼                 ▼
  ┌──────────┐      ┌──────────┐     ┌───────────────┐
  │  failed  │      │   paid   │     │ manual_review │ amount/currency mismatch,
  └────┬─────┘      └────┬─────┘     └───────┬───────┘ PENDING capture, fraud flag
       │ retry           │ grants issued     │ admin approves
       ▼                 ▼                   │
  ┌──────────┐     ┌────────────┐            │
  │ cancelled│     │ completed  │◄───────────┘
  └──────────┘     └─────┬──────┘
                         │ refund
                         ▼
                   ┌──────────┐
                   │ refunded │  grants revoked
                   └──────────┘
```

Encoded as `OrderStatus` enum with an explicit transition table:

```php
public function canTransitionTo(self $next): bool
{
    return in_array($next, match ($this) {
        self::Pending      => [self::Paid, self::Failed, self::ManualReview, self::Cancelled],
        self::Paid         => [self::Completed, self::ManualReview, self::Refunded],
        self::ManualReview => [self::Completed, self::Cancelled, self::Refunded],
        self::Completed    => [self::Refunded],
        self::Failed       => [self::Cancelled, self::Pending],
        self::Cancelled,
        self::Refunded     => [],
    }, true);
}
```

`OrderService::transition()` is the **only** code permitted to write `orders.status`. It asserts the
transition, writes inside a transaction, appends an audit log entry, and fires the matching domain
event. An invalid transition throws — it is a bug, not a user error.

`processing` from the source plan is intentionally dropped: for digital goods the window between
`paid` and `completed` is a queue job measured in milliseconds, and a status nobody ever sees is a
status nobody should maintain.

### 5.2 Events and listeners

| Event | Listeners (queued unless noted) |
|---|---|
| `OrderPlaced` | `SendOrderConfirmation` |
| `OrderPaid` | `IssueDownloadGrantsListener`, `IncrementProductSalesCount`, `RecordCouponUsage` (sync) |
| `OrderCompleted` | `SendDownloadEmail`, `UpdateCustomerAggregates` |
| `OrderFlaggedForManualReview` | `NotifyAdminsOfManualReview` |

### 5.3 The `Money` value object

```php
final readonly class Money
{
    private function __construct(public int $cents, public string $currency) {}

    public static function fromCents(int $c, string $cur = 'USD'): self;
    public static function fromDecimal(string $d, string $cur = 'USD'): self;  // "12.50"
    public function plus(self $o): self;       // asserts matching currency
    public function minus(self $o): self;
    public function percentage(int $pct): self; // integer math, banker-safe rounding
    public function toDecimalString(): string;  // "12.50" — PayPal wants exactly this
    public function format(string $locale = 'en_US'): string;
}
```

Every price in the system is a `Money`. Floating-point currency never enters the codebase. The
`toDecimalString()` method exists because PayPal's API requires a string with exactly two decimal
places, and generating that from a float is the classic source of one-cent mismatches.

## 6. PayPal integration — the centrepiece

**Requirement:** as easy as WooCommerce — paste the keys and it works. We will go one step further:
WooCommerce makes the owner register the webhook by hand in the PayPal developer dashboard. We do
it for them, automatically, with one click.

### 6.0 The provider interface

PayPal is the only provider at launch. It is nonetheless built **behind an interface**, because the
cost of doing so now is roughly one day, and the cost of extracting it later — once checkout,
refunds, the admin and the order state machine all speak PayPal directly — is a rewrite.

```php
interface PaymentProvider
{
    public function key(): string;                 // 'paypal', 'free', 'stripe', 'paddle'
    public function isConfigured(): bool;
    public function supportsRefunds(): bool;

    public function createPayment(Order $order): PaymentIntent;
    public function capture(Order $order, string $providerOrderId): PaymentResult;
    public function refund(Payment $payment, Money $amount, string $reason): RefundResult;

    public function verifyWebhook(Request $request): bool;
    public function parseWebhook(array $payload): ?WebhookEventData;

    public function healthCheck(): HealthReport;
    public function settingsSchema(): array;       // drives the admin form automatically
}
```

Three implementations are planned, two of which ship at launch:

| Implementation | Status | Purpose |
|---|---|---|
| `PayPalProvider` | Launch | The real thing (§6.1–6.10) |
| `FreeProvider` | Launch | Zero-total orders, no payment step at all (§7.6) |
| `MerchantOfRecordProvider` | Future | Tax handled by the provider; see §7.8 |

The rules that keep the abstraction honest:

- `PaymentProvider` returns **domain objects** (`PaymentIntent`, `PaymentResult`), never raw
  provider JSON. The moment a controller reads `$response['purchase_units'][0]`, the interface has
  failed.
- `settingsSchema()` means a new provider brings its own admin form. No one edits the settings page
  to add a provider.
- `Order` carries `provider` as a string. Nothing outside `app/Services/Payments/PayPal/` mentions
  PayPal by name.
- Each provider owns its own webhook route (`/webhooks/{provider}`), sharing the idempotency ledger
  in §6.7.

A migration to a merchant of record then means writing one class and one adapter — roughly a week,
not a quarter.

### 6.2 What happens on "Save and enable payments"

```
1. Validate the two strings are non-empty and well-formed.
2. POST /v1/oauth2/token  with Basic auth → prove the credentials work.
   ✗ 401 → "These credentials were rejected by PayPal. Check that you copied them
            from the LIVE app, not the Sandbox app."  (mode-aware message)
3. GET  /v1/identity/oauth2/userinfo (or a cheap authenticated probe)
   → display the merchant name so the owner can confirm they pasted the right account. [VERIFY]
4. GET  /v1/notifications/webhooks  → is a webhook already pointing at our URL?
   a. Yes, with the correct event list → store its id. Done.
   b. Yes, with a stale event list   → PATCH it to the correct list.
   c. No                             → POST /v1/notifications/webhooks to create it.
5. Store the returned webhook id under `paypal.{mode}.webhook_id`.
6. Set `paypal.enabled = true`, flush settings cache, write an audit log entry.
7. Green banner: "PayPal is live. Your store can now accept payments."
```

Steps 4–6 are what WooCommerce makes a human do. Automating them removes the single most common
cause of "my orders are stuck as pending" support tickets: a missing or misconfigured webhook.

### 6.3 `PayPalClient` — transport and auth

Responsibilities: base URL selection, OAuth token caching, retries, logging, error mapping.
Nothing else.

```php
final class PayPalClient
{
    public function __construct(
        private readonly PayPalConfig $config,   // resolved from Settings (§3.2)
        private readonly CacheRepository $cache,
        private readonly LoggerInterface $log,
    ) {}

    public function token(): string
    {
        // Cache key is namespaced by mode AND by a hash of the client id, so rotating
        // credentials or flipping mode instantly invalidates the cached token.
        $key = "paypal:token:{$this->config->mode}:" . substr(
            hash('sha256', $this->config->clientId), 0, 16
        );

        return $this->cache->remember($key, fn () => $this->fetchToken(), /* see below */);
    }

    private function fetchToken(): string
    {
        $res = Http::asForm()
            ->withBasicAuth($this->config->clientId, $this->config->clientSecret)
            ->timeout($this->config->timeout)
            ->retry($this->config->retries, 200, throw: false)
            ->post($this->config->baseUrl . '/v1/oauth2/token',
                   ['grant_type' => 'client_credentials']);

        if ($res->failed()) {
            throw PayPalAuthException::fromResponse($res);
        }

        // Store for (expires_in - 300) seconds: never serve a token about to expire.
        return $res->json('access_token');
    }

    public function request(string $method, string $path, array $payload = [],
                            array $headers = []): array;
}
```

Hard rules:

- **Token TTL** = `expires_in` minus a 300-second safety margin. PayPal tokens last ~9 hours; a
  token that expires mid-capture is a lost sale.
- **Automatic single retry on 401**: clear the cached token, re-authenticate, replay once. Covers
  credential rotation and clock skew.
- **`PayPal-Request-Id`** header on every POST that creates or captures. This is PayPal's
  idempotency key. We derive it deterministically — `"order-{$order->uuid}"` for create,
  `"capture-{$order->uuid}"` for capture — so a retried request after a network timeout returns the
  *original* result instead of charging twice.
- **Never log** the client secret or the full `Authorization` header. The logging middleware
  redacts both by key name.
- **Circuit breaker**: after 5 consecutive 5xx responses within 60 seconds, open the breaker for
  120 seconds and surface a clean "PayPal is temporarily unavailable, please try again shortly"
  on the storefront instead of a stack trace.

### 6.4 Creating the order

`POST {base}/v2/checkout/orders`

```json
{
  "intent": "CAPTURE",
  "purchase_units": [{
    "reference_id": "MA-1048",
    "custom_id": "<order uuid>",
    "invoice_id": "MA-1048",
    "description": "Monera Art — 3 digital items",
    "amount": {
      "currency_code": "USD",
      "value": "14.97",
      "breakdown": {
        "item_total": { "currency_code": "USD", "value": "17.97" },
        "discount":   { "currency_code": "USD", "value": "3.00" }
      }
    },
    "items": [
      { "name": "Mid-Century Modern Coffee Bar Wall Art",
        "quantity": "1",
        "unit_amount": { "currency_code": "USD", "value": "5.99" },
        "category": "DIGITAL_GOODS" }
    ]
  }],
  "payment_source": {
    "paypal": {
      "experience_context": {
        "brand_name": "Monera Art",
        "shipping_preference": "NO_SHIPPING",
        "user_action": "PAY_NOW",
        "return_url": "https://moneraart.com/checkout/paypal/return",
        "cancel_url": "https://moneraart.com/checkout/paypal/cancel"
      }
    }
  }
}
```

Non-negotiable details:

- **`category: DIGITAL_GOODS`** on every item and **`shipping_preference: NO_SHIPPING`**. Without
  these, PayPal collects a shipping address we neither need nor want to store, and the buyer sees
  an irrelevant address step.
- **`user_action: PAY_NOW`** makes the PayPal button say "Pay Now" instead of "Continue", which
  measurably reduces drop-off at the final step.
- **`custom_id`** carries our order UUID. It comes back on the webhook payload, which is how we
  reconnect an event to an order even if our own `provider_order_id` write failed.
- **The breakdown must sum exactly.** `item_total - discount == amount.value`, to the cent. PayPal
  rejects the order otherwise. This is precisely why §5.3 forbids floats.
- **Amounts are computed server-side from the database**, never read from the request body. The
  browser sends product ids and a coupon code; nothing else about money is trusted.

Our order row is created with status `pending` **before** the PayPal call, inside a transaction, so
a captured payment can never arrive for an order that does not exist.

### 6.5 Capture and verification

`POST {base}/v2/checkout/orders/{id}/capture` with `PayPal-Request-Id`.

The response is then validated in this exact order — each check can route the order to
`manual_review` instead of failing silently:

```php
1. status === 'COMPLETED'
       'PENDING'  → manual_review, reason = capture_pending (PayPal risk hold)
       'DECLINED' → failed
2. capture currency_code === order currency              → else manual_review
3. capture amount value, parsed to cents, === order total → else manual_review (CRITICAL)
4. capture id not already present in `payments`           → else return the existing payment
5. persist Payment{status: completed, fee_cents, net_cents from seller_receivable_breakdown}
6. OrderService::transition($order, Paid)
7. IssueDownloadGrants
8. transition → Completed, dispatch SendDownloadEmail
```

Check 3 is the one that matters. An attacker who tampers with the client-side amount gets an order
parked in `manual_review` with a loud flag, not a free download.

### 6.6 Webhook auto-provisioning

```php
final class PayPalWebhookService
{
    private const EVENTS = [
        'CHECKOUT.ORDER.APPROVED',
        'PAYMENT.CAPTURE.COMPLETED',
        'PAYMENT.CAPTURE.DENIED',
        'PAYMENT.CAPTURE.REFUNDED',
        'PAYMENT.CAPTURE.REVERSED',
        'CUSTOMER.DISPUTE.CREATED',   // so the admin learns about a dispute from us
    ];

    public function provision(): WebhookProvisionResult
    {
        $url = route('webhooks.paypal');            // https://.../webhooks/paypal

        // A non-public URL can never receive a webhook. Fail loudly and early.
        if (! $this->isPubliclyReachable($url)) {
            return WebhookProvisionResult::skipped(
                'Your site is not reachable from the internet yet, so PayPal cannot '
                . 'deliver notifications. Payments will still work, but orders may need '
                . 'manual approval. Re-run this once the site is live.'
            );
        }

        $existing = collect($this->client->request('GET', '/v1/notifications/webhooks')['webhooks'] ?? [])
            ->firstWhere('url', $url);

        if ($existing) {
            return $this->syncEventTypes($existing);   // PATCH if the list drifted
        }

        $created = $this->client->request('POST', '/v1/notifications/webhooks', [
            'url'         => $url,
            'event_types' => array_map(fn ($n) => ['name' => $n], self::EVENTS),
        ]);

        Settings::set("paypal.{$this->mode}.webhook_id", $created['id']);

        return WebhookProvisionResult::created($created['id']);
    }
}
```

Local development note: PayPal cannot reach `localhost`. The system-check step of the setup wizard
detects a non-public host and prints the exact `ngrok`/`expose` command to run, plus a reminder to
set `APP_URL`. The developer never has to discover this by watching orders hang.

### 6.7 Webhook receipt — the idempotency path

Route: `POST /webhooks/paypal`, in `routes/webhooks.php`, with **no CSRF, no session, no auth
middleware**, rate-limited to 300/min per IP.

```php
public function __invoke(Request $request, PayPalWebhookService $webhooks): Response
{
    $payload = $request->json()->all();
    $eventId = $payload['id'] ?? null;

    if (! $eventId) {
        return response()->noContent(400);
    }

    // 1. Signature verification BEFORE anything else touches the payload.
    $verified = $webhooks->verifySignature($request);

    if (! $verified) {
        Log::warning('paypal.webhook.signature_failed', ['event_id' => $eventId]);
        // 403, not 200: an unverified event must be retried, not silently dropped.
        return response()->noContent(403);
    }

    // 2. The unique index IS the lock. A duplicate insert means we already have it.
    try {
        $event = WebhookEvent::create([
            'provider'            => 'paypal',
            'event_id'            => $eventId,
            'event_type'          => $payload['event_type'],
            'resource_type'       => $payload['resource_type'] ?? null,
            'resource_id'         => data_get($payload, 'resource.id'),
            'signature_verified'  => true,
            'payload'             => $payload,
            'status'              => 'received',
            'received_at'         => now(),
        ]);
    } catch (UniqueConstraintViolationException) {
        return response()->noContent(200);   // already seen — acknowledge and stop
    }

    // 3. Acknowledge fast, process off the request cycle.
    ProcessPayPalWebhook::dispatch($event->id);

    return response()->noContent(200);
}
```

Why it is built this way:

- **Verify before parse.** Nothing from an unverified payload reaches business logic.
- **403 on bad signature, not 200.** PayPal retries non-2xx responses. If our webhook id is briefly
  wrong, a 200 would permanently discard real payment events; a 403 means PayPal keeps trying while
  we fix the configuration.
- **Insert, then dispatch.** The row exists before the job runs, so a worker crash loses nothing —
  a scheduled sweeper re-dispatches any `received` row older than five minutes.
- **Respond in milliseconds.** PayPal times out slow endpoints and marks them unhealthy.

**Signature verification** calls `POST /v1/notifications/verify-webhook-signature` with
`transmission_id`, `transmission_time`, `cert_url`, `auth_algo`, `transmission_sig`, our stored
`webhook_id`, and the raw event body, expecting `verification_status === "SUCCESS"`.

Two additional guards:

1. **Validate `cert_url` against an allowlist of PayPal-owned hosts before sending it anywhere.**
   An attacker who controls `cert_url` and finds a lenient verifier could otherwise redirect
   certificate fetching. Reject any host not matching `*.paypal.com`.
2. **Verify against the raw request body**, not a re-encoded array. `json_encode(json_decode($x))`
   is not byte-identical to `$x`, and signature checks are byte-sensitive.

### 6.8 Capture vs. webhook — which one wins

Both paths can complete an order, and both will run for a normal purchase. They converge safely:

- The **capture response** is the fast path. The customer is waiting; this is what gets them to the
  download page in ~2 seconds.
- The **webhook** is the reliable path. It arrives even if the customer closed the tab, lost
  connectivity, or our server restarted mid-request.

Both call the same `MarkOrderPaid` action, which begins with
`SELECT ... FOR UPDATE` on the order row and returns early if the order is already `paid` or
`completed`. Combined with the unique index on `provider_capture_id`, double-fulfilment is
impossible at two independent layers.

### 6.9 Refunds

`POST /v2/payments/captures/{capture_id}/refund`. Admin-triggered only, full or partial, always
with a reason, always audit-logged. On success: record the refund, transition the order to
`refunded`, revoke every related download grant, and send the refund email. A
`PAYMENT.CAPTURE.REFUNDED` webhook arriving for a refund initiated in PayPal's own dashboard runs
the identical path, so refunds issued outside our admin still revoke access.

### 6.10 Payment health check (dashboard widget)

A scheduled check every 15 minutes, surfaced as a dashboard tile:

| Check | Degraded when |
|---|---|
| OAuth token obtainable | any failure |
| Webhook registered and matching our URL | missing or drifted |
| Last webhook received | > 24 h with orders present in that window |

### 6.11 Running several stores on one PayPal account

The owner already sells through an existing WordPress/WooCommerce store. This new store must feed
the **same PayPal business account**, so both sites deposit into one balance.

**This works, and nothing in the design has to change.** PayPal credentials are not bound to a
domain. One business account can serve any number of sites.

The right way to set it up:

```
PayPal Business Account  (one balance, one withdrawal)
│
├── REST App "chrisdelgstudio"   → Client ID + Secret → webhook → chrisdelgstudio.com
└── REST App "moneraart"         → Client ID + Secret → webhook → moneraart.com
```

Create a **separate REST App per site** in the PayPal developer dashboard rather than reusing one
set of credentials. It costs nothing and buys three things:

1. **Separate webhooks.** Webhooks are registered per app, so each store receives only its own
   events. Sharing credentials would deliver every WooCommerce event to our endpoint and vice
   versa — our handler would reject them as unknown orders, but the noise makes any real incident
   harder to diagnose.
2. **Independent revocation.** If one site's credentials leak, you rotate that app alone. The other
   store keeps selling.
3. **Attribution.** Transactions from both stores land in one account, so they must be
   distinguishable. We already send `invoice_id` and `custom_id` on every order (§6.4); prefixing
   the order number per store (`MA-1048` here, something else there) makes PayPal's own reports and
   any accounting export sort cleanly without extra work.

**What the customer sees.** The `brand_name` in `experience_context` (§6.4) controls the name shown
during the PayPal flow. Set it to the store's name, and a buyer on this site sees *Monera Art* even
though the underlying account is shared. Set it per store, not globally.

**The one real caveat:** a shared account means **shared risk**. PayPal evaluates disputes,
chargeback ratios and account standing at the *account* level, not per site. A problem originating
in one store can limit or freeze funds for both. If the two stores ever diverge meaningfully in
risk profile — different product categories, very different price points, one of them experimental —
separate business accounts are the safer structure. At current volume, one account is fine; it is
worth revisiting if either store grows substantially. See §24.1.

### 6.12 Fee structure — this materially changes the pricing model

PayPal's standard rate is weighted toward the **fixed** component, which is brutal on low-priced
digital goods. PayPal also offers a **micropayments** rate with the opposite shape — higher
percentage, much lower fixed fee.

**[VERIFY both rates for the account's country before relying on these numbers; they vary by
market and change.]** Illustrative US rates: standard **3.49% + $0.49**, micropayments
**4.99% + $0.09**.

| Sale price | Standard — you keep | Micropayments — you keep | Difference |
|---|---|---|---|
| $1.99 | $1.43 (28% lost) | **$1.80** (10% lost) | +26% revenue |
| $2.99 | $2.40 (20% lost) | **$2.75** (8% lost) | +15% revenue |
| $4.99 | $4.33 (13% lost) | **$4.65** (7% lost) | +7% revenue |
| $9.99 | $9.15 (8% lost) | **$9.40** (6% lost) | +3% revenue |
| $14.99 | $13.98 (7% lost) | $14.15 (6% lost) | +1% revenue |
| $26.67 | — break-even — | — break-even — | 0 |
| $40.00 | **$38.11** | $37.91 | standard wins |

The crossover sits near **$26.67**. Below it, micropayments wins; above it, standard does.

For a catalog priced $1.99–$20, micropayments is the correct rate, and at the $1.99 floor it is
worth **roughly 26% more revenue per sale** — far more than any conversion optimisation we could
realistically achieve on the storefront.

Action items:

- Request micropayments pricing from PayPal for the account **[VERIFY availability in the account's
  country — it is not offered everywhere, and historically it has sometimes required a separate
  linked account]**.
- Treat $1.99 as the **floor price**, confirmed by the owner. Below that, the fixed fee alone
  dominates regardless of rate.
- Push bundles and multi-item carts hard. One $14.99 cart of six pieces nets far more than six
  separate $2.49 sales, because the fixed fee is charged **per transaction, not per item**. This is
  a cart-design conclusion, not just a marketing one: see §14.1.
- Cross-border sales add roughly **1.5%** plus a currency conversion spread **[VERIFY]**. Selling
  worldwide in USD, assume an effective rate above the headline figure when modelling margins.

## 7. Cart and checkout

### 7.1 Cart storage

Server-side, in the Redis-backed session, keyed by product id. Digital goods have no variants and
quantity is always 1, so the cart is a small id list — no snapshot of prices, which are always
re-resolved from the database at render and at checkout.

Adding an item is a normal form POST that works without JavaScript; Alpine intercepts it to update

**Cart badge and full-page caching.** A cart counter in the header would normally make every page

### 7.4 Order success page

`/order/{uuid}` — reachable via a signed URL valid for 7 days and linked from the confirmation
email, so a customer who closes the tab can still return. It lists every file with a direct download
button, shows the expiry and remaining-downloads counters, and repeats the support email. It is
`noindex, nofollow` and sent with `Cache-Control: no-store`.

### 7.5 Abandoned and stuck orders

A scheduled job every 10 minutes:

- `pending` older than 2 hours, no payment → `cancelled`, release coupon reservation.
- `pending` with a `provider_order_id` → actively query PayPal for its real status before
  cancelling. **Never cancel an order without asking PayPal first** — a paid order cancelled by a
  timeout is the worst possible outcome.
- `webhook_events` in `received` older than 5 minutes → re-dispatch.

### 7.6 Free products

A product priced at zero must cost the customer **nothing and no friction**: no card, no PayPal, no
account. Email address, download, done.

This is handled by `FreeProvider` (§6.0), not by special-casing the checkout:

```
cart total === 0
   → checkout shows only: email + terms checkbox + [ Get your free art ]
   → no PayPal SDK loaded at all (saves ~90 KB of third-party JS on that path)
   → Order created with is_free = true, total_cents = 0
   → FreeProvider::capture() returns an immediate success with no Payment row
   → Order → paid → completed, grants issued, email sent
```

No `payments` row is created, because no payment occurred. Reports filter on `orders.is_free` so a
free download never pollutes revenue figures.

**Abuse control.** Free files are the one surface a stranger can drain without paying, and the
defences must not punish real customers:

| Control | Setting |
|---|---|
| Free orders per IP | 3 / hour, 10 / day |
| Free orders per email address | 5 / day |
| Disposable email domains | Rejected against a maintained blocklist |
| Download expiry on free grants | Shorter by default (24 h vs 72 h), configurable |
| Max free items per cart | Configurable, default 3 |

Deliberately **not** required: email confirmation before the download link is sent. A
double-opt-in step before delivery roughly halves completion, and the file is being given away. The
link goes to the address supplied; if the address is wrong, nobody receives anything, which is its
own sufficient control.

**Why this is worth building.** Free products are the cheapest list-building mechanism available to
a store like this — the customer arrives, receives something real, and the email address is captured
with explicit marketing consent. It is also the lowest-risk way to test which styles convert before
committing to a paid collection.

### 7.7 Terms acceptance at checkout

The customer must actively accept the terms before paying. This is both a legal requirement in
several of the markets this store sells into and the mechanism by which the no-refund policy
becomes enforceable at all (§7.7.2).

#### 7.7.1 The checkout control

```
☐  I have read and agree to the Terms of Sale and Privacy Policy, and I
   understand that I am purchasing immediate access to digital files that
   are non-refundable once delivered.
   ─────────────────       ──────────────
   (opens in a new tab)    (opens in a new tab)
```

Implementation rules:

- **Unchecked by default.** A pre-ticked box is not consent, and in the EU it is explicitly invalid.
- **Required.** The pay button stays disabled until it is ticked, and the server **re-validates**
  acceptance before creating the PayPal order. A disabled button is a UI convenience, not a control.
- **Links open in a new tab** (`target="_blank" rel="noopener"`), so a customer reading the terms
  never loses their cart.
- **One checkbox, not four.** Separate boxes for terms, privacy, refunds and AI disclosure measurably
  increase abandonment and add nothing: the single statement covers all of it, and every linked
  document is one click away.
- **Marketing consent is a separate, optional, unticked box.** Bundling marketing consent into a
  required terms checkbox invalidates it under GDPR. Keep them apart.

#### 7.7.2 Recording acceptance

On order creation, persist `terms_version`, `terms_accepted_at` and `terms_accepted_ip_hash` (§4.2).

Terms documents are **versioned and immutable**: editing the terms in the admin creates a new
version rather than overwriting the current one, and every past version stays retrievable. The order
detail screen links to the exact revision that customer accepted.

This exists for one reason. In a PayPal dispute, the question is not "what do your terms say" but
"what did this buyer agree to on this date" — and a policy edited since the sale is worthless as
evidence. Three columns and a versioned document turn an unanswerable question into a one-click
answer.

#### 7.7.3 What the no-refund policy can and cannot do

Stated plainly, because building the feature without understanding its limits would be misleading:

- **EU and UK consumers have a statutory 14-day right of withdrawal** on digital content. It can be
  waived — but only if the customer **expressly consents to immediate delivery and acknowledges
  losing the right**. That acknowledgement is precisely what the checkout wording above provides.
  Without it, "no refunds" is unenforceable in those markets and the customer wins every dispute.
- **PayPal Buyer Protection operates independently of your terms.** A buyer can open a dispute
  regardless of what they agreed to, and PayPal decides. Notably, PayPal Seller Protection
  **does not cover digital goods**, so the evidence that matters is your own: the acceptance record,
  delivery timestamps, and download logs (§8.4). Every one of those is already captured by this
  design — this is why §4.3 logs downloads rather than merely counting them.
- **A no-refund policy should still allow discretionary refunds.** Duplicate purchases, corrupt
  files and genuine mistakes are cheaper to refund than to argue about, and a refund issued by you
  costs far less than a dispute lost to PayPal. The policy sets the default; the admin keeps the
  override (§13.4).

### 7.8 Taxes — the launch position

**At launch the store does not calculate, collect or remit any sales tax or VAT.** Prices are
charged exactly as listed.

This is a deliberate decision taken at current volume (~$100/month), not an oversight. The reasoning,
the real exposure, and the trigger for revisiting it are recorded in §24.4 so that the decision is
auditable later rather than forgotten.

What the build does now to keep the door open:

- `orders.tax_cents` exists and is always `0`. The column, the totals arithmetic and the order
  display already carry tax; only the calculation is absent.
- The `PaymentProvider` interface (§6.0) means switching to a merchant of record — which makes tax
  someone else's statutory problem — is one adapter class, not a checkout rewrite.
- `customers.country` is captured from the PayPal payer record where available, so if tax becomes
  necessary there is historical data to assess exposure against, rather than a blank slate.

**Revisit when:** monthly revenue sustains ~$1,000, or EU/UK sales exceed roughly a quarter of
orders, or the business is formally registered. Whichever comes first.

## 8. Digital delivery

### 8.1 Storage layout

```
storage/app/private/products/{product_uuid}/{file_uuid}.{ext}      ← sellable, never served directly
storage/app/public/catalog/{product_uuid}/{hash}-{w}.{webp|avif}   ← derived previews, CDN-cacheable
```

The private disk is outside the web root. In S3 it is a bucket with **Block Public Access on** and
no bucket policy granting anonymous reads. Filenames are UUIDs, so even a leaked path reveals
nothing about the catalog.

### 8.2 Token design

```php
$token = bin2hex(random_bytes(32));                 // 64 hex chars, 256 bits
$grant->token_hash = hash('sha256', $token);        // only the hash is stored
$url = route('download', ['token' => $token]);      // /d/{token}
```

The plaintext token exists only in the email and the success page. A database dump yields no usable
download links — the same reasoning that applies to password hashes.

### 8.3 Grant issuance

`IssueDownloadGrants` runs inside the `OrderPaid` transaction:

```
for each order_item:
    resolve file ids from item.file_manifest   (frozen at purchase time)
    for a bundle: union of all child products' files, deduplicated by checksum
    for each file:
        create grant: fresh token, expires_at = now + settings.download.expiry_hours (default 72),
                      max_downloads = settings.download.max_downloads (default 5)
```

Bundles reference the same physical files as their children — one byte on disk, many grants. A
"Complete Bundle" of 60 artworks costs 60 small rows, not 60 duplicated files.

### 8.4 Serving the file

```php
public function __invoke(string $token, DownloadService $downloads): Response
{
    // Narrow rate limit: 20 attempts / minute / IP. Token enumeration is pointless
    // against 256 bits, but we refuse to be a bandwidth amplifier.
    $grant = $downloads->resolve(hash('sha256', $token));   // single indexed lookup

    return match (true) {
        $grant === null                           => $this->deny('not_found', 404),
        $grant->revoked_at !== null               => $this->deny('revoked', 410),
        $grant->expires_at->isPast()              => $this->deny('expired', 410),
        $grant->download_count >= $grant->max_downloads => $this->deny('limit', 429),
        default                                   => $downloads->stream($grant),
    };
}
```

Expired and limit-reached responses render a friendly page with a **"Request a new link"** button,
which emails a fresh grant to the order's address — no support ticket, no admin involvement, and no
way for a stranger to trigger it, because the new link only ever goes to the original buyer's inbox.

**Streaming mechanics** (never `readfile()` through PHP):

- Local disk → `X-Accel-Redirect` to an Nginx `internal` location. PHP decides; Nginx transfers.
  Memory use stays flat regardless of file size, and a 200 MB bundle does not tie up a PHP worker.
- S3 → a pre-signed URL with a 60-second TTL and a `response-content-disposition` header forcing the
  original filename. The customer's browser talks to S3 directly.

Counters increment **before** the stream begins, and a `download_logs` row is written in both the
success and failure cases.

### 8.5 Lifecycle

- Refund → all grants for the order revoked immediately.
- Admin actions: *Regenerate* (new token, resets counters, invalidates the old link), *Extend*
  (push `expires_at`), *Revoke*. All audit-logged with the acting user.
- `CleanupExpiredDownloads` runs nightly: grants expired more than 90 days are deleted;
  `download_logs` are retained for 1 year, then pruned.

### 8.6 Storage drivers — local now, Cloudflare R2 when needed

Launch on the server's local disk. Switch to R2 from the admin, without a deploy, when it is worth
it. Nothing in the application changes: `product_files.disk` already exists in the schema (§4.1), and
`FileStreamer` picks its mechanism from the driver.

#### 8.6.1 The problem a pre-signed URL creates

This is the part worth getting right, because the obvious implementation quietly breaks the download
limit.

A pre-signed R2 or S3 URL is **a bearer token for that file**. Whoever holds it can download, as many
times as they like, until it expires. R2 does not count downloads, does not know about orders, and
cannot be told "allow five and then stop".

So if a confirmation email contains a pre-signed URL valid for 72 hours:

- `max_downloads = 5` is decorative. The URL works an unlimited number of times.
- Forwarding the email, or pasting the link anywhere, hands over the product permanently for 72
  hours.
- Revoking access is impossible. The URL stays valid until it expires, whatever the database says.

**A pre-signed URL must never be the link the customer receives.**

#### 8.6.2 The design: our server authorises, R2 transfers

The customer's permanent link always points at **our** server. The pre-signed URL exists for
seconds, inside a redirect, and is never stored or emailed.

```
Customer clicks  https://moneraart.com/d/{token}          ← this is what's in the email
       │
       ▼
Our server:  resolve token by hash        (one indexed lookup)
             revoked?  expired?  count >= max?             ← the limit is enforced HERE
             increment download_count
             write download_logs row
       │
       ▼
302 redirect → https://<r2>/…?X-Amz-Expires=60&…          ← lives 60 seconds
       │
       ▼
Browser downloads straight from R2        ← our server moves no bytes
```

Why this resolves the tension:

- **The counter lives in our database** and is checked on our server, on every single attempt. The
  limit is real.
- **Revocation is immediate.** A revoked grant stops issuing redirects, and whatever URL was last
  issued has already expired.
- **Bandwidth bypasses our server entirely.** We pay for one 302, not for a 200 MB transfer.
- **The customer's link is permanent and shareable-but-useless** — sharing it shares a link that
  checks the counter before serving anything.

**The residual risk, stated honestly:** someone can capture the redirect target and reuse it within
its 60-second window. That is acceptable, and the alternative is not better:

- The counter has already been incremented, so the attempt is spent regardless
- 60 seconds is long enough to download and far too short to distribute
- The realistic threat is a customer forwarding their email to a friend, which this stops completely

Shortening the window further starts failing legitimate downloads on slow connections, which trades
a theoretical problem for a real one.

#### 8.6.3 Mechanism per driver

| Driver | Mechanism | Bytes through PHP | Bytes through our server |
|---|---|---|---|
| `local` | `X-Accel-Redirect` → Nginx `internal` location | None | Yes |
| `r2` / `s3` | 302 → 60-second pre-signed URL | None | **None** |

Both sit behind one method, so the controller never knows which is active:

```php
final class FileStreamer
{
    public function serve(ProductFile $file, string $filename): Response
    {
        return match ($file->disk) {
            'local' => response()->noContent(200, [
                'X-Accel-Redirect'    => '/protected/' . $file->path,
                'Content-Disposition' => $this->disposition($filename),
                'Content-Type'        => $file->mime_type,
            ]),
            default => redirect()->away(
                Storage::disk($file->disk)->temporaryUrl(
                    $file->path,
                    now()->addSeconds(60),
                    ['ResponseContentDisposition' => $this->disposition($filename)]
                )
            ),
        };
    }
}
```

`ResponseContentDisposition` matters: without it the browser downloads a file named after the UUID
on disk. With it, the customer gets `mid-century-coffee-bar-wall-art-16x20.pdf`.

#### 8.6.4 Why R2 rather than S3

For this store the deciding factor is not storage price — it is **egress**.

Selling print-ready files means 20–80 MB per order, sometimes more for a full bundle. S3 charges for
every byte leaving the bucket. **R2 charges nothing for egress** **[VERIFY current pricing]**.

Illustrative, 500 orders in a month at 50 MB each (25 GB transferred, 50 GB stored):

| | S3 | R2 |
|---|---|---|
| Storage | ~$1.15 | ~$0.75 |
| Egress | ~$2.25 | **$0** |
| Requests | ~$0.01 | ~$0.01 |
| **Total** | **~$3.41** | **~$0.76** |

Small numbers at this volume — but egress is the line that scales with sales, and it is the one line
R2 removes entirely. A viral product on S3 produces a bandwidth bill proportional to its success. On
R2 it does not.

R2 is S3-API-compatible, so Flysystem's existing S3 adapter works with `region: 'auto'` and the R2
endpoint. Pre-signed URLs are supported **[VERIFY against current R2 docs]**.

```php
'r2' => [
    'driver'   => 's3',
    'key'      => Settings::get('storage.r2.access_key_id'),
    'secret'   => Settings::get('storage.r2.secret_access_key'),
    'region'   => 'auto',
    'bucket'   => Settings::get('storage.r2.bucket'),
    'endpoint' => 'https://' . Settings::get('storage.r2.account_id')
                  . '.r2.cloudflarestorage.com',
    'use_path_style_endpoint' => true,
    'visibility' => 'private',
],
```

**The bucket stays fully private.** No public access, no custom domain binding, no public
development URL. Every byte leaves through a pre-signed URL our server issued. A private bucket
accidentally made public is the one configuration mistake that gives away the entire catalog, so the
storage settings page checks for public accessibility and refuses to activate a bucket that responds
to an unauthenticated request.

#### 8.6.6 Migration between drivers

```
php artisan storage:migrate --to=r2 [--dry-run]
```

Queued, per file, resumable, and safe to run on a live store:

```
for each product_file where disk != target:
    stream file from source → target        (never loaded fully into memory)
    re-read from target, verify sha256 against product_files.checksum_sha256
    checksum mismatch → log, skip, leave the source file untouched
    match → update product_files.disk inside a transaction
    source file deleted only after a configurable retention window (default 7 days)
```

Three properties that make this survivable:

- **Checksum verification before switching** the disk column. A silently truncated upload would
  otherwise sell a corrupt file.
- **`disk` is per file**, not global, so a half-finished migration is a valid state. Downloads keep
  working for files on either side.
- **Source files are retained**, not deleted on success. A week to notice a problem and flip back by
  reverting the column.

Reverse direction works identically (`--to=local`), so this is not a one-way door.

#### 8.6.7 Public images

Preview images (§10) are a different problem with a different answer. They are public by design,
cached hard at the edge, and never secret.

- Local disk: Nginx serves them directly with a one-year immutable cache header, Cloudflare caches
  them at the edge.
- R2: the public bucket can be bound to a custom domain (`cdn.moneraart.com`) and served through
  Cloudflare's CDN for free.

Public and private storage are **separate buckets**, always. Mixing sellable files and preview
images in one bucket means one permission mistake exposes the catalog.

### 8.7 Customer access to past purchases — without accounts

A related question: how does a customer get back to files they bought last month?

The plan deliberately has no customer accounts (§7.2) — no passwords to store, breach or reset, and
no field at checkout anyone has to fill in. But "my download links expired and I've lost the email"
still needs an answer better than emailing support.

**Passwordless lookup** gives permanent access without creating accounts:

```
/orders  →  "Enter the email you used to buy"
         →  we email a signed link, valid 30 minutes, single use
         →  /orders/{signed}  lists every order for that email,
            with fresh download grants issued on demand
```

Why this beats accounts for this store:

- **Nothing new at checkout.** Still one email field. Zero added friction at the exact moment
  friction costs money.
- **No passwords.** Nothing to store, hash, rotate, reset, or leak. The §9 attack surface does not
  grow at all.
- **Enumeration-safe.** The page says "if that address has orders, we've sent a link" whether or not
  it does, so nobody learns who shops here.
- **Works for everyone**, including customers who bought before this feature existed.
- **Rate limited** to 3 requests per hour per email, so it cannot be used to mail-bomb anyone.

The lookup page reuses `customers.email_hash` (§9.3) for the search, so no new index or query path
is needed — it is roughly a day of work, and it removes an entire category of support email.

If customer accounts are ever genuinely wanted — a saved library, wishlists, re-download history —
they can be added later on top of this, since `customers` already exists and is keyed by email hash.
The passwordless link is the 90% answer for 10% of the cost, and it should ship first either way.

## 9. Customer data protection

### 9.1 What we store, and why so little

| Field | Stored | Form |
|---|---|---|
| Email | Yes — required to deliver | Encrypted + blind index |
| Name | Optional | Encrypted |
| IP address | No | SHA-256 HMAC only (abuse detection) |
| Postal address | **No** | — |
| Phone | **No** | — |
| Card data | **No, ever** | PayPal's problem, by design |

### 9.2 Encryption

Application-level AES-256-GCM via Laravel's encrypter, applied through an `encrypted` model cast.
The key lives in `APP_KEY`, in the environment, never in the database and never in a backup
alongside the data it protects.

### 9.3 Blind index — making encrypted email searchable

Encrypted values are not searchable (`WHERE email = ?` cannot work when every ciphertext is
randomised). The standard answer:

```php
final class BlindIndex
{
    public static function email(string $email): string
    {
        return hash_hmac('sha256', mb_strtolower(trim($email)), config('app.blind_index_key'));
    }
}
```

- `BLIND_INDEX_KEY` is a **separate** 32-byte secret from `APP_KEY`. Compromising one does not
  compromise the other.
- HMAC, not a plain hash: a plain `sha256(email)` is trivially reversible against a dictionary of
  known addresses. The keyed construction is not.
- Supports **exact lookup only**. "Find customers whose email contains *gmail*" is impossible by
  design — which is why `email_domain` is stored separately in clear text for the analytics that
  legitimately need it.

Admin search on customers therefore searches by exact email, by order number, or by name — and the
UI says so plainly instead of silently returning nothing.

### 9.4 Key rotation

A documented, tested procedure — not an aspiration:

```
php artisan store:rotate-keys --new-key=base64:...
  1. Put the application in maintenance mode.
  2. Chunk through customers: decrypt with the old key, re-encrypt with the new.
  3. Recompute blind indexes if the blind-index key is also rotating.
  4. Swap APP_KEY (keeping the old one in APP_PREVIOUS_KEYS during the window).
  5. Verify a sample decrypts; exit maintenance mode.
```

Laravel's `APP_PREVIOUS_KEYS` makes the window safe: old ciphertext keeps decrypting while new
writes use the new key.

### 9.5 Retention and data subject requests

- Orders and payments: retained 7 years (tax/accounting), then the customer record is anonymised —
  encrypted fields nulled, `email_hash` replaced with a random value, order rows kept for the books.
- `php artisan store:gdpr-export {email}` → JSON of everything held about a person.
- `php artisan store:gdpr-delete {email}` → anonymise as above; audit-logged.
- Download logs: 1 year. Audit logs: 2 years.

## 10. Image pipeline and artwork protection

> This section addresses a gap in the source plan. A digital art store must display its product to
> sell it, and the product *is* an image. Without deliberate protection, the storefront is a free
> download page with extra steps.

### 10.1 Two classes of image, never mixed

| | Preview (`product_images`) | Deliverable (`product_files`) |
|---|---|---|
| Disk | `public`, CDN-served | `private`, token-gated |
| Max dimension | 1920 px | original (often 6000 px+) |
| Resolution | 72 dpi | 300 dpi |
| Watermark | Yes, on the largest sizes | No |
| Metadata | Stripped | Preserved |

A preview is never good enough to print at size; a deliverable is never reachable without a grant.

### 10.2 Derivative generation (queued on upload)

```
Upload original  (validated: real MIME sniffing, dimension cap, ≤50 MB)
   → strip EXIF/GPS/ICC except the colour profile
   → extract dominant colour + blurhash (for zero-CLS placeholders)
   → generate widths [320, 640, 960, 1280, 1920]
   → encode each as WebP (q82) and AVIF (q55)
   → apply watermark to the 1280 and 1920 variants
   → write the variant map to product_images.variants
   → purge the CDN path for this product
```

### 10.2.1 Measured on this machine — GD is viable, memory is the constraint

Benchmarked rather than assumed. A synthetic 6000×4000 original through the full fan-out
(five widths × WebP + AVIF), PHP 8.5 with GD:

| Width | WebP | AVIF | Output size |
|---|---|---|---|
| 320 | 0.010 s | 0.064 s | 18 / 15 KB |
| 640 | 0.029 s | 0.102 s | 40 / 29 KB |
| 960 | 0.050 s | 0.751 s | 61 / 32 KB |
| 1280 | 0.085 s | 0.193 s | 85 / 42 KB |
| 1920 | 0.163 s | 0.232 s | 129 / 61 KB |
| **Total** | **≈ 3.0 s** | | **peak RSS 188 MB** |

Two conclusions, and the second is the one that matters:

**Speed is a non-issue.** Three seconds for ten derivatives runs on the `media` queue where nobody
is waiting. The original plan's preference for libvips was about an order of magnitude on a
operation that is already fast enough. GD also supports **both WebP and AVIF** on this build, so
nothing in §10.2 has to change.

**Memory is the real constraint.** A 6000×4000 truecolor raster is 96 MB in GD before any work
begins, and the peak lands at 188 MB. Against PHP's default `memory_limit` of 128 M, the first
real upload would have crashed — so `memory_limit` is now **512 M**, and that is a deployment
requirement, not a local convenience.

This also makes the dimension cap in §16.5 **load-bearing rather than a security nicety**. Memory
scales with pixel count: an 8000×8000 upload needs roughly 256 MB for the source raster alone, and
a deliberately crafted image is a trivial denial of service. The cap is enforced at **50
megapixels**, checked from the image header *before* the file is decoded.

Production guidance: web processes 256 M (they never process images — it is queued), queue workers
512 M or more. Install libvips where the host allows it; it lowers the memory ceiling considerably
and is the better choice at volume. GD is the floor, and the floor is high enough.

### 10.3 Watermarking

A low-opacity (8–12%) tiled mark across the large variants. Visible enough to make a screenshot
useless as a print, subtle enough not to spoil the browsing experience. Configurable in settings
(image, opacity, scale, on/off), with a live preview in the admin so the owner can tune it without
a developer.

Explicitly **not** attempted: right-click blocking, `oncontextmenu` handlers, transparent overlay
divs, "image protection" scripts. They are trivially bypassed, they break accessibility and
keyboard use, and they signal distrust to legitimate customers. Resolution limits plus watermarks
are the only defences that actually hold.

### 10.4 The responsive image component

```blade
<x-art-image :image="$product->cover" sizes="(max-width: 768px) 100vw, 50vw"
             loading="lazy" fetchpriority="auto" />
```

Renders a `<picture>` with AVIF and WebP sources, explicit `width`/`height` (so layout shift is
zero), the dominant colour as a background placeholder, and the stored alt text. The LCP image on
each page passes `loading="eager" fetchpriority="high"` and is preloaded in the document head.

## 11. SEO implementation

### 11.1 Metadata generation

`GenerateSeoMetadata` runs on publish and on update, and **only writes rows where
`is_auto_generated` is true** (§4.5).

| Field | Generation rule |
|---|---|
| `seo_title` | `{title} — {primary attribute} Printable Wall Art \| {store}` truncated at 60 chars on a word boundary |
| `seo_description` | First 155 chars of the description, sentence-boundary trimmed, with format and file count appended |
| `canonical_url` | Always the absolute `/art/{slug}` — never a filtered or parameterised variant |
| `og_image` | 1200×630 render: artwork on a neutral ground with the store mark, generated by the image pipeline |
| `alt_text` | `{title} — {style} {room} printable wall art` |
| `slug` | Slugified title; on collision append a short numeric suffix |

Every field is editable in the product form. The form shows a live Google-style SERP preview and a
character counter, so the owner can see the effect without knowing what a meta description is.

**On AI-assisted copy:** optional, off by default, and always producing a *suggestion* the admin
accepts or rejects — never silent auto-publication. Thin auto-generated text at scale is the
fastest route to an algorithmic penalty, which is the one SEO mistake that is expensive to undo.

### 11.2 Structured data

A `<x-json-ld>` component emitting `Product` + `Offer` on product pages, `CollectionPage` +
`ItemList` on collections, `BreadcrumbList` everywhere, and `WebSite` + `Organization` on the home
page. Built from the same Eloquent model that renders the visible page, so the structured price and
availability cannot drift from the displayed ones — the single most common cause of a Search Console
structured-data penalty.

`availability` is always `https://schema.org/InStock` (digital goods never run out), and
`priceValidUntil` reflects the sale end date when one is set.

### 11.3 URL scheme and redirects

```
/                                home
/shop                            all products, paginated
/art/{slug}                      product          ← canonical, permanent
/collections/{slug}              collection
/style/{slug}  /room/{slug}      attribute landing pages (only when is_seo_landing)
/about /contact /terms /privacy /refund-policy
```

A model observer on `Product` fires `ProductSlugChanged` whenever a **published** product's slug
changes, synchronously creating a 301 from the old path. Draft products change slugs freely without
generating redirect clutter.

`HandleSeoRedirects` middleware runs early, looks up `from_hash` (one indexed query, Redis-cached),
and issues 301 / 302 / 410 as configured. Archived products return **410 Gone** rather than 404:
410 tells search engines the removal is intentional and de-indexes faster.

### 11.4 Sitemaps

Generated by a queued job, written as static XML to the public disk, served by Nginx directly:

```
/sitemap.xml              index
/sitemaps/products.xml    published products, lastmod = updated_at
/sitemaps/collections.xml indexable collections only
/sitemaps/pages.xml       static pages
/sitemaps/images.xml      cover + gallery images with captions and titles
```

Regenerated on publish/unpublish/delete (debounced to at most once every 5 minutes) and nightly as a
safety net. Chunked at 50,000 URLs per file. The image sitemap matters disproportionately here:
image search is a primary discovery channel for printable art.

### 11.5 Index control

`noindex, nofollow` on `/cart`, `/checkout`, `/order/*`, `/d/*`, `/admin`, `/setup`, internal search
results, and every filtered or sorted listing variant. `robots.txt` is generated from settings, so
the owner can toggle "allow search engines to index this store" during a soft launch without
touching a file.

Faceted browsing is crawlable for *humans* but carries `noindex` plus a canonical pointing at the
unfiltered parent — which is how we honour the source plan's requirement that filters must not spawn
thousands of duplicate indexable URLs.

A collection or attribute page only gains `is_indexable` once it holds at least
`min_products_for_index` (default 4) published products. A nightly job maintains this both ways: a
collection that drops below the threshold loses indexability and is removed from the sitemap.

```php
Route::get('/',                        Home::class)->name('home');

Route::get('/art/{product:slug}',      ProductShow::class)->name('product');

Route::get('/collections/{slug}',      CollectionShow::class)->name('collection');

Route::get('/cart',                    CartShow::class)->middleware('noindex');

     ->middleware(['signed', 'noindex'])->name('order.success');
Route::get('/d/{token}',               DownloadController::class)
     ->middleware(['throttle:downloads', 'noindex'])->name('download');
```

### 12.2 Visual direction — character without complexity

The brief is **simple, fast, easy, everything within reach — and with a style of its own.** Those
pull in opposite directions only if you look for character in the wrong place.

> **Character is free. Complexity is not.**
>
> A site's personality comes from **typography, colour, scale and layout rhythm**. All four are
> plain CSS: no JavaScript, no payload, no accessibility cost, no effect on the §12.6 budget.
>
> What people usually reach for when a site "needs personality" — carousels, scroll animations,
> parallax, hover effects, video headers, custom cursors — adds weight, breaks screen readers,
> and makes a site feel *busy* rather than distinctive.
>
> This store takes all of the first list and none of the second.

#### 12.2.1 Typography does most of the work

One distinctive display face, used large and confidently, carries an entire identity on its own. It
is the highest-impact, lowest-cost decision available.

- **Display face** — something with a point of view for titles and headings. A high-contrast
  editorial serif or a characterful grotesque. **Not** Playfair, Montserrat or Poppins: those three
  read as "template" to anyone who looks at websites, which includes everyone shopping for art.
- **Text face** — one quiet, highly legible sans for UI, prices, and body copy. Its job is to
  disappear.
- **Two families. Four weights. Nothing else.** Self-hosted WOFF2, subset to Latin + Latin Extended
  (Spanish needs the accents), `font-display: swap`, display face preloaded.

**Scale contrast is where the character lives.** A 72 px title above a 11 px letterspaced label
feels editorial and considered. The same content at 24 px and 16 px feels like a template. The
contrast costs nothing.

```
PRINTABLE · MID-CENTURY          ← 11px, uppercase, 0.12em tracking, muted
Coffee Bar                       ← 72px display face, tight leading
Wall Art                         ←
Six pieces · 300 DPI · $14.99    ← 15px text face
```

#### 12.2.2 Palette

Warm, not white. A gallery is bone and ink, not an office document.

```
Ink        #16140F   body text, headings
Paper      #FAF7F0   page background
Muted      #595751   secondary text — contrast-checked, see §12.4.4
Rule       #E2DDD2   hairlines, borders
Accent     one saturated colour, used three or four times per page at most
```

The artwork supplies all the colour on the page. The interface stays out of its way. An accent that
appears everywhere stops being an accent.

#### 12.2.3 The wall label

The one distinctive component in the system, and it is pure HTML and CSS.

Every product is presented the way a gallery presents a piece — a printed placard beside the work:

```
┌──────────────────────┐
│                      │   ── 014 ──────────────────────
│                      │
│      [artwork]       │   Mid-Century Modern
│                      │   Coffee Bar Wall Art
│                      │
└──────────────────────┘   Digital print · 2024
                           300 DPI · 2:3, 3:4, 4:5, A-series
                           6 files · instant download

                           $14.99
```

Why this earns its place:

- It is **immediately recognisable as an art store** rather than a shop that happens to sell images.
- It is **structured text**, which means it is also the accessible version — the a11y requirement and
  the design choice are the same artifact, not a compromise between them.
- It is **free**: a definition list and a border rule.
- It gives every product page the same quiet confidence, whatever the artwork looks like.

The numbered index (`014`) runs through listings, product pages and collections. Small detail, costs
nothing, and it reads as a catalogue rather than a feed.

#### 12.2.4 Layout rhythm

- **Asymmetric grid.** Twelve columns, but content does not fill them evenly. A title block sitting
  in columns 2–7 with the rest empty reads as deliberate; centred content reads as default.
- **Varied card sizes** in listings, on a repeating rhythm — large, small, small, large — instead of
  a uniform matrix. This single decision is most of what separates a gallery from a WooCommerce
  grid, and it is one CSS Grid rule.
- **Pieces break the gutter** occasionally. One full-bleed artwork per page, no more.
- **Whitespace: 96–128 px between sections** on desktop, 56 px on mobile. Leave it empty. The
  instinct to fill space is the instinct that produces generic layouts.
- **Hairline rules** instead of boxes and cards with shadows. A 1px line in `Rule` does the
  separating work that a drop shadow does, with more restraint.

#### 12.2.5 Motion

Opacity and 8–16 px translate. 200–300 ms. Entirely inside
`@media (prefers-reduced-motion: no-preference)`.

No parallax, no scroll-triggered reveals down the whole page, no counters, no marquees, no custom
cursor.

#### 12.2.6 Explicitly banned, because they are what make a site generic

| Pattern | Why not |
|---|---|
| Hero carousel / slider | Nobody sees slide 2. Accessibility and LCP both suffer. |
| Three-column icon row ("Fast delivery · Secure payment · Support") | The single most template-looking element on the web |
| Everything centred | Centred text is the default, and defaults read as defaults |
| Card grid with drop shadows and rounded corners | This is the WooCommerce look the brief rules out |
| Gradient buttons, glassmorphism, neumorphism | Dated on arrival, and they fight the artwork |
| Stock photos of anything | An art store showing stock photography is a contradiction |
| Badges shouting SALE / NEW / HOT | A gallery does not shout |
| Countdown timers, "17 people viewing" | Manufactured urgency, and it reads as distrust |

#### 12.2.7 Everything within reach

"Simple" must not mean "things are hard to find". Four rules:

- **Search is visible on every page**, in the header, never hidden behind an icon that opens a
  modal. For an art store, search is primary navigation (§12.7).
- **Maximum two levels of hierarchy.** Shop → Collection → Product. There is no third level.
- **Every product page offers a way onward**: more from this collection, similar style, similar
  room. A dead end at the bottom of a product page is a lost visit.
- **Breadcrumbs on every page below the home**, as real links. They orient the visitor, they feed
  `BreadcrumbList` structured data (§11.2), and they cost one line of markup.

#### 12.2.8 Product page composition

Artwork occupies **at least 60% of the first viewport**. The wall label sits beside it on desktop,
beneath it on mobile. Price and the buy button are reachable without scrolling but visually quiet —
no large coloured block, no sticky bar following the visitor down the page.

The artwork is the argument. The interface only has to not interrupt it.

### 12.3 Page composition

**Home** — one full-bleed featured artwork, a short editorial statement, three curated collections,
a new-arrivals row, and the trust strip (instant download, secure PayPal, formats included).

**Product** — gallery with a mockup toggle (framed in a room / flat), title, price, the one-line
pitch, a buy button, an accordion with included files, print sizes and ratios, then "More from this
collection" and "You may also like". All text is server-rendered HTML (SEO requirement), the
accordion uses `<details>` so it works with JavaScript disabled.

**Shop** — filters as plain links (no JS required), sorting via query parameters, pagination with
`rel=prev/next`. Filtered views are `noindex` + canonical to the parent.

### 12.4 Accessibility — target WCAG 2.2 Level AA

**Release-blocking, not aspirational.** A page that fails these does not ship.

Two reasons this gets real investment rather than a checklist at the end. First, an image-heavy
store is exactly the kind of site that excludes people by default — if the artwork carries the
information and the artwork has no text equivalent, a blind customer has no store. Second, the
buying audience for wall art skews older, and the most common accessibility failures — low-contrast
grey text, tiny touch targets, text that breaks when zoomed — are the same things that lose those
customers. This is conversion work that happens to also be the right thing to do.

#### 12.4.1 Foundations

| Requirement | Specific rule |
|---|---|
| Semantic structure | Real landmarks (`header`, `nav`, `main`, `footer`), one `<h1>` per page, no skipped heading levels |
| Contrast | **4.5:1** body text, **3:1** large text and UI components. See 12.4.4 — this is where design-led stores fail |
| Focus | `:focus-visible` on everything interactive, 2px offset ring, never `outline: none` |
| Touch targets | **44×44px minimum** (WCAG 2.2 requires 24; 44 is the usable number) |
| Zoom | Usable at 200% with no horizontal scroll; reflows at 400% |
| Text spacing | Survives the WCAG text-spacing override without clipping |
| Motion | All animation inside `prefers-reduced-motion: no-preference` |
| Language | `lang` attribute correct per locale, `hreflang` on the language switcher |
| Images | Every meaningful image has alt text; decorative images carry `alt=""` |
| Forms | Visible label on every field, errors tied via `aria-describedby`, correct `autocomplete` |

#### 12.4.2 The components that actually need thought

Most of the page is static HTML and is accessible for free. Four things are not:

**Product gallery / lightbox** — the hardest component on the site.
Opens with focus moved to the dialog, `role="dialog"` + `aria-modal="true"`, focus trapped inside,
Escape closes and returns focus to the trigger, arrow keys move between images, current position
announced ("Image 2 of 6"). If this proves hard to get right, **ship a simple non-modal gallery
instead** — a scroll-through strip is fully accessible with no JavaScript, and an inaccessible
lightbox is worse than no lightbox.

**Product cards** — a whole-card click target is good UX and a screen-reader hazard, because the
naive implementation announces the same destination two or three times (image link, title link,
button). One real `<a>` wrapping the title carries the accessible name; the card surface extends the
click area via a pseudo-element overlay. One link announced, whole card clickable.

**Filters** — plain `<a>` links, never JS-only controls. The active filter carries `aria-current`,
and an `aria-live="polite"` region announces the new count ("24 artworks"). Without that
announcement, a screen-reader user who applies a filter gets silence and no way to know anything
changed.

**Cart updates** — adding to cart announces via `aria-live`, and the focus stays where the user put
it. Never move focus to a toast.

#### 12.4.3 Search accessibility

Because search is a priority (§12.7), it gets explicit treatment: a `role="search"` landmark, a
labelled input, the instant-results dropdown implemented as a proper combobox
(`aria-expanded`, `aria-controls`, `aria-activedescendant`), arrow-key navigation through results,
Escape to close, and result counts announced politely. **The form submits and works with JavaScript
disabled** — the dropdown is enhancement, the form is the product.

#### 12.4.4 The contrast trap in this specific design

§12.2 asks for "generous whitespace, minimal UI, editorial restraint". The house style of that
aesthetic is light grey text on white, and it fails contrast almost every time.

Hard rules for the design system:

- Body text: `#111` on `#FAF8F5` — ratio ~17:1, no argument possible
- Secondary text: never lighter than `#595959` on that background (4.5:1 floor)
- **Placeholder text is not a label** and never carries information
- Price and availability: full-contrast body colour, never "subtle"
- Disabled controls still meet 3:1 against their background
- Colour is never the only carrier of meaning — a sale price gets a label, not just a red

Every token in the palette is contrast-checked **once, at design time**, and the checked pairs are
documented. Checking at review time means discovering the problem after the whole site is built on
it.

#### 12.4.5 How it is verified

| Method | When | Catches |
|---|---|---|
| axe-core in CI, all key pages | Every PR | ~40% of issues — the mechanical ones |
| Keyboard-only walkthrough of a full purchase | Before each release | Focus traps, unreachable controls, lost focus |
| NVDA (Windows) + VoiceOver (macOS/iOS) on home, product, cart, checkout | Before launch, then quarterly | The ~60% automation cannot catch |
| 200% and 400% zoom pass | Before each release | Layout breakage |
| Lighthouse accessibility | Every PR, **score must be 100** | Regressions |

Automated testing alone is the single most common way a site gets declared accessible while being
unusable. A real keyboard-and-screen-reader pass through an actual purchase is the only test that
proves the store works.

**The acceptance criterion for launch:** a person using only a keyboard and a screen reader can find
an artwork, understand what they are buying, complete checkout, and download their files — without
sighted assistance.

### 12.7 Search

Search is how people actually shop an art store. A visitor who knows they want *something blue for
the kitchen* will not browse twelve collection pages to find it. Search has to be fast, forgiving of
typos, bilingual, and useful when it finds nothing.

#### 12.7.1 Engine choice

| Option | Verdict |
|---|---|
| MySQL FULLTEXT | Free and already in the schema, but no typo tolerance, weak relevance ranking, poor on short queries. Fine as a fallback, not as the product. |
| **Meilisearch** | **Chosen.** Typo tolerance built in, sub-50 ms, ~50–100 MB RAM, native per-language indexes, faceting included, first-party Laravel Scout driver. |
| Typesense | Equivalent; Meilisearch wins on simpler operations for a single small instance. |
| Algolia | Excellent and hosted, but a recurring cost and sends the catalog to a third party. Revisit only at much larger scale. |

Meilisearch runs on the same server as everything else. It is one more process, not one more
machine.

**Typo tolerance is the feature that justifies the dependency.** Real queries look like
`mid centry modern`, `minimalsta cocina`, `coffe bar art`. MySQL FULLTEXT returns nothing for all
three. Meilisearch returns the right results for all three, with no configuration. Every one of
those zero-result queries would otherwise be a visitor who leaves.

#### 12.7.2 Index design

One index **per locale** — `products_en`, `products_es` — never a shared index with a language
field. Stemming, stop words and typo rules differ per language, and mixing them degrades both.

```json
{
  "id": 142,
  "title": "Mid-Century Modern Coffee Bar Wall Art",
  "subtitle": "Warm retro tones for a kitchen nook",
  "description": "…",
  "slug": "mid-century-modern-coffee-bar-wall-art",
  "collections": ["Retro Kitchen", "Coffee Bar"],
  "style": ["mid-century", "retro"],
  "room":  ["kitchen", "dining-room"],
  "theme": ["coffee", "beverages"],
  "color": ["amber", "cream", "walnut"],
  "ratio": ["2:3", "3:4", "4:5"],
  "price_cents": 599,
  "is_bundle": false,
  "file_count": 12,
  "sales_count": 48,
  "published_at": 1760000000,
  "cover": { "url": "…", "alt": "…", "width": 640, "height": 800 }
}
```

Searchable attributes, in ranked order: `title` → `subtitle` → `collections` → `style`, `room`,
`theme`, `color` → `description`. Order matters: a title match must always outrank a description
match.

Filterable: `style`, `room`, `theme`, `color`, `ratio`, `price_cents`, `is_bundle`, `collections`.
Sortable: `price_cents`, `sales_count`, `published_at`.

Ranking rules: `words → typo → proximity → attribute → sales_count:desc → exactness`. Putting
`sales_count` before `exactness` means that among equally relevant results, the ones people actually
buy surface first.

Only **published** products in the locale's catalog are indexed (§4.7.2). Indexing is queued on
save, so a product edit never blocks on the search engine, and a Meilisearch outage degrades the
store to browsing rather than taking it down.

#### 12.7.3 What the customer gets

**Instant dropdown** (enhancement, keyboard-accessible per §12.4.3) — fires after 200 ms of
inactivity and 2+ characters, showing at most 5 products with thumbnails, up to 2 matching
collections, and a "see all N results" row.

Matching **collections appear above products**, deliberately. A query like `coffee bar` is better
answered by one curated landing page than by sixteen loose products — it is a better experience and
it sends the visitor to a page that converts harder.

**Results page** `/en/search?q=…` — server-rendered, works with no JavaScript, `noindex` (§11.5),
with facets for style, room, colour and price as plain links.

**Zero results is a designed page, not an error.** This is where most stores silently lose people:

```
No artwork matched "midcentry kitchn"

Did you mean: mid-century kitchen →          ← typo correction from the engine

Browse instead:
  [Kitchen art]  [Mid-Century]  [Retro]      ← closest matching attributes

Popular right now:
  [four product cards]                       ← never a dead end
```

A visitor always leaves the zero-results page with somewhere to go.

#### 12.7.4 Learning from search

```
search_queries:  id, query varchar(255), locale char(5), results_count int,
                 clicked_product_id null, clicked_position tinyint null,
                 session_hash char(64), created_at
                 index (locale, created_at), index (query(64))
```

No personal data — `session_hash` is a salted hash that allows "did this search lead to a click"
without identifying anyone.

The admin gets one screen with three lists: top queries, **queries returning zero results**, and
queries with no clicks.

The zero-results list is the single most valuable report in the entire admin panel. It is a list of
things customers came looking for and you do not sell — written by the customers themselves, in
their own words, in both languages. It is a product roadmap that costs nothing to generate.

#### 12.7.5 Performance

| Metric | Budget |
|---|---|
| Dropdown response | < 50 ms |
| Results page TTFB | < 150 ms |
| Index update after product save | < 5 s |
| Memory footprint | < 150 MB |

The dropdown queries Meilisearch directly through a scoped, search-only API key, debounced and with
in-flight requests cancelled. Common queries are cached in Redis for 5 minutes.

**Graceful degradation:** if Meilisearch is unreachable, search falls back to MySQL FULLTEXT
automatically and logs the failure. Degraded search beats a broken page.

### 12.8 Simplicity rules

"Simple" is not a mood, it is a set of decisions someone can be held to.

| Rule | Why |
|---|---|
| **Three clicks** from home to a completed purchase | Home → product → checkout. Anything longer means something was inserted that should not be there. |
| **No popups.** No newsletter modal, no exit-intent, no "wait, 10% off!" | They raise email capture slightly and damage trust, speed and accessibility considerably. The free products in §7.6 build the list better and treat people better. |
| **No cookie banner** | We set no advertising or analytics cookies (§Privacy). Strictly-necessary cookies are exempt from consent requirements in the EU, so there is nothing to ask about. This is a genuine competitive advantage: no banner, no consent library, no layout shift, no friction. **It only holds if nobody adds Google Analytics later.** |
| **Max 5 top-level navigation items** | Shop · Collections · About · Search · Cart |
| **No account required**, ever, for buying | Already decided in §7.2 |
| **One-page checkout**, three fields | Email, coupon, consent |
| **No carousels** | Poor accessibility, poor performance, near-zero engagement past the first slide |
| **No infinite scroll** | Breaks the footer, breaks back-button position, breaks screen readers. Pagination with real `<a>` links. |
| **No chat widget** | ~100 KB of third-party JavaScript to replace an email address that answers in [RESPONSE_WINDOW] |
| **No video backgrounds, no splash, no intro animation** | |

**The test applied to any proposed addition:** does this help someone find art they want and buy it?
If the honest answer is "it helps us", it does not ship.

## 14. Pricing mechanics and coupons

### 14.1 Cart value is the unit that matters

The fee analysis in §6.12 has a direct consequence for how the cart and promotions are built: PayPal
charges a fixed fee **per transaction, not per item**. Six separate $2.49 sales and one $14.94 cart
of the same six pieces are very different outcomes.

| Scenario | Gross | Fees (micropayments) | Net |
|---|---|---|---|
| 6 separate $2.49 orders | $14.94 | $1.29 | **$13.65** |
| 1 cart of 6 at $14.94 | $14.94 | $0.84 | **$14.10** |
| 1 bundle priced $12.99 | $12.99 | $0.74 | **$12.25** |

The bundle nets less than the full-price cart but **converts far better**, and the comparison that
matters is against the realistic alternative — one $2.49 sale, netting $2.29.

Concrete requirements that follow:

- **Floor price $1.99.** Enforced as validation in the product form, not merely documented, with the
  reason shown inline so it is not mistaken for an arbitrary limit.
- **Bundles are first-class, not an afterthought.** The product page shows "part of a 6-piece
  collection — save 40%" with one-click upgrade from single to set. This is the single highest-value
  conversion element on the page.
- **Cart-level nudges**: "add 2 more pieces and save 25%" as a progress indicator toward the next
  tier.
- **Quantity-tier coupons** (buy 3 save 20%, buy 6 save 35%) are automatic, not code-entered — a
  discount the customer has to discover and type is a discount most customers never get.
- **Free items never trigger the paid path** (§7.6), so a cart of only free items has no fee at all.

### 14.2 Coupon validation

Validation order, short-circuiting on the first failure, each with its own customer-facing message:

```
1. exists and is_active
2. within starts_at / expires_at
3. usage_limit not reached
4. usage_limit_per_customer not reached (by email_hash)
5. cart subtotal >= min_subtotal_cents
6. scope matches at least one cart item (all | products | collections)
7. compute discount on the matching subset only
8. cap at max_discount_cents
9. final total never below zero
```

Validation runs **again, server-side, at capture time**. A coupon that expires between page load and
payment must not apply — this is a real and routinely exploited race.

`coupon_usages` is written inside the order transaction with a unique constraint on
`(coupon_id, order_id)`, so a concurrent double-submit cannot consume two uses.

Admin: code (uppercased, with a generate button), type, value, scope picker, limits, window, active
toggle, and a usage report showing orders, revenue and discount given.

### 16.1 Headers (`SecurityHeaders` middleware)

```
Strict-Transport-Security: max-age=31536000; includeSubDomains; preload
X-Content-Type-Options: nosniff
X-Frame-Options: DENY                       (SAMEORIGIN on admin)

Cross-Origin-Opener-Policy: same-origin
Content-Security-Policy: (see below)
```

### 16.2 CSP

```
default-src 'self';
script-src  'self' 'nonce-{random}' https://www.paypal.com https://www.paypalobjects.com;
style-src   'self' 'nonce-{random}';
img-src     'self' data: https://www.paypalobjects.com https://{cdn};
frame-src   https://www.paypal.com;
connect-src 'self' https://www.paypal.com;
font-src    'self';
object-src  'none';
base-uri    'self';
form-action 'self' https://www.paypal.com;
frame-ancestors 'none';
upgrade-insecure-requests;
report-uri /csp-report
```

Nonce-based, never `unsafe-inline`. Deployed in `Content-Security-Policy-Report-Only` for one week
first, reports reviewed, then enforced — enforcing an unvalidated CSP on a live checkout is how you
break payments on a Friday.

### 16.3 Rate limits

| Surface | Limit |
|---|---|
| Admin login | 5 / min / IP, 10 / hour / email, then lockout + alert |
| Checkout create order | 10 / min / IP |
| Checkout capture | 10 / min / IP |
| Coupon apply | 20 / min / IP (blocks brute-force code discovery) |
| Downloads | 20 / min / IP |
| Download renewal request | 3 / hour / order |
| Webhooks | 300 / min / IP |
| Contact form | 5 / hour / IP + honeypot + timing check |

### 16.4 Admin authentication

Argon2id (`memory_cost` 64 MB, `time_cost` 4, `threads` 2). Mandatory TOTP 2FA with recovery codes,
enforced at wizard step 3 and non-removable afterwards. Sessions: 2-hour idle timeout, absolute
12-hour cap, regenerated on login, `HttpOnly` + `Secure` + `SameSite=Lax`. Optional IP allowlist.
Admin path configurable (default `/admin`) so it is not at the obvious URL. Email alert on login
from an unrecognised IP.

### 16.5 Upload validation

Real MIME sniffing with `finfo` (never the client-supplied `Content-Type`), extension allowlist,
size cap (50 MB images / 200 MB deliverables, configurable), image dimension cap to prevent
decompression bombs, re-encode of all preview images (which destroys any embedded payload), random
UUID filenames, and storage outside the web root. SVG uploads are either rejected or passed through
a strict sanitiser — an SVG is an executable document, not an image.

### 16.6 Input and output

Form Requests validate every endpoint. Eloquent everywhere (no raw SQL without bindings). Blade
escapes by default; `{!! !!}` appears only for product descriptions, which pass through an HTML
sanitiser with a tight tag allowlist on the way *in*. Policies on every model, with a default-deny
`Gate::before` for non-owner roles.

### 16.7 The "never trust the client" list

| Value | Where it actually comes from |
|---|---|
| Price | `products` table, at checkout time |
| Discount | Server-side coupon validation |
| Total | Recomputed server-side and re-verified against PayPal's capture |
| Payment status | PayPal's API response and verified webhook, only |
| Product identity | Database lookup by id, with a published-status check |
| Download authorisation | `download_grants` row lookup by token hash |
| Admin capability | Policy check, every time, server-side |

## 19. Observability

- **Errors**: Sentry (or equivalent), with `APP_KEY`, PayPal secrets and customer PII scrubbed in

- **Logs**: structured JSON, daily rotation, 30-day retention. Dedicated channels for `payments`,

## 21. Testing

### 21.1 Money paths (must exist before launch)

```
✓ full checkout, sandbox PayPal, reaches completed and issues grants
✓ capture amount mismatch       → manual_review, no grants issued
✓ capture currency mismatch     → manual_review
✓ capture returns PENDING       → manual_review
✓ capture returns DECLINED      → failed, no grants
✓ duplicate webhook (same event_id)      → exactly one payment row
✓ webhook arriving before capture returns → exactly one payment row
✓ webhook with an invalid signature      → 403, nothing persisted
✓ webhook with a tampered cert_url       → rejected before any outbound call
✓ concurrent capture + webhook (parallel) → exactly one fulfilment
✓ client-side price tampering            → server price wins
✓ coupon expiring between load and pay   → rejected at capture
✓ coupon usage limit under concurrency   → never exceeded
✓ refund                                 → grants revoked, order refunded
```

### 21.2 Delivery

Valid token streams · expired → 410 · revoked → 410 · limit reached → 429 · unknown token → 404
(timing-safe) · counters increment exactly once · every attempt logged · bundle grants cover the
union of child files · regeneration invalidates the old token.

**Storage drivers** (§8.6) — these catch the expensive mistakes:

```
✓ local driver returns X-Accel-Redirect, never file bytes through PHP
✓ r2 driver returns a 302 whose target expires in 60 seconds
✓ a pre-signed URL is NEVER written to an email, a page, or the database
✓ hitting /d/{token} six times with max_downloads = 5 is refused on the sixth,
  even though every previous redirect target was a valid pre-signed URL
✓ a revoked grant stops redirecting immediately
✓ Content-Disposition carries the real filename, not the storage UUID
✓ storage:migrate verifies sha256 before switching product_files.disk
✓ a checksum mismatch during migration leaves source file and disk column untouched
✓ a half-migrated catalog serves downloads correctly from both drivers
✓ the private bucket refuses an unauthenticated GET  ← the settings page asserts this too
```

**Passwordless order lookup** (§8.7): a known email receives a link · an unknown email gets an
identical response · the signed link expires in 30 minutes · it is single-use · rate limited to
3/hour/email.

### 21.3 Security

Unauthenticated admin access → redirect · support role cannot refund · private storage path is not
web-reachable · upload of a renamed `.php` file is rejected · XSS payload in a product description
is sanitised · rate limits enforce · CSP header present · customer email is ciphertext in the raw DB
row · blind index finds the customer, `LIKE` on ciphertext does not.


### 22.2 Deployment

Zero-downtime via atomic release symlink:

```
1. composer install --no-dev --optimize-autoloader
2. npm ci && npm run build
3. php artisan migrate --force
4. php artisan config:cache route:cache view:cache event:cache
5. symlink switch
6. php artisan horizon:terminate   (workers restart on new code)
7. reload php-fpm
8. smoke test: GET /, GET a product page, assert 200 + price present
9. roll back on smoke-test failure
```

Migrations must be backwards-compatible with the previous release (expand → migrate → contract),
so step 9 is always available.

## 23. Build order

Each phase ends in something demonstrable. Estimates assume one experienced Laravel developer;
halve the calendar with two.

### Phase 0 — Foundation (3–5 days)
Laravel + Filament skeleton, Docker local environment, CI pipeline, settings system (§3.2), setup
wizard shell, encryption helpers, private/public disks, base layouts.
**Done when:** `/setup` runs end to end on a clean database and CI is green.

### Phase 1 — Catalog (5–7 days)
Migrations 01–04, models, policies, product/collection/attribute Filament resources, image pipeline
with watermarking, file uploads.
**Done when:** the owner can create a product with artwork and deliverables entirely through the UI.

### Phase 2 — Storefront (11–15 days)
Design system first (type, palette, wall label, grid rhythm — §12.2), then home, shop, product,
collection and attribute pages, responsive images, cart, breadcrumbs, **legal pages with versioned
documents** (terms, privacy, refunds, licence, AI disclosure — text drafted in
[legal_content.en.md](./legal_content.en.md) and [legal_content.es.md](./legal_content.es.md)),
AI disclosure badge on product pages.
**Done when:** the catalog browses beautifully on a phone, Lighthouse ≥ 95, and every legal page
renders with a visible version and effective date.

### Phase 2b — Search (4–6 days)
Meilisearch setup, per-locale indexes, queued indexing, instant dropdown built as an accessible
combobox, server-rendered results page with facets, designed zero-result page, `search_queries`
logging, MySQL FULLTEXT fallback, admin search-insights screen.
**Done when:** every *Search* item in §21.4 passes, including the typo queries.

### Phase 2c — Accessibility pass (4–5 days)
Full WCAG 2.2 AA work: contrast token audit, gallery keyboard behaviour, filter live regions, card
link structure, zoom and reflow, axe-core wired into CI, keyboard-only purchase, NVDA and VoiceOver
passes.
**Done when:** every *Accessibility* item in §21.4 passes, Lighthouse a11y = 100, and a purchase has
been completed end to end using only a keyboard and a screen reader.

### Phase 3 — Payments (8–12 days) ← the critical phase
`PaymentProvider` interface, `PayPalProvider`, `FreeProvider` (zero-total path), order creation,
capture + verification, webhook endpoint with idempotency, auto webhook provisioning, payments
settings UI with test connection, checkout page with terms acceptance and acceptance recording,
order state machine.
**Done when:** every test in §21.1 passes against the PayPal sandbox, a free product downloads with
no payment step, acceptance is recorded with its terms version, and a non-technical person can
configure payments from the admin in under three minutes.

### Phase 4 — Delivery (6–9 days)
Grants, tokens, `FileStreamer` with both drivers (X-Accel-Redirect for local, 60-second pre-signed
redirect for R2/S3), download and success pages, self-service renewal, expiry/limit/revocation,
cleanup job, **storage settings page with its four verification checks**, `storage:migrate` command,
**passwordless order lookup** (§8.7).
**Done when:** buy → email → download works end to end on the local driver, §21.2 passes including
every storage-driver test, and the same suite passes again with the driver switched to R2.

Build both drivers now even though launch is local-only. The whole point of §8.6.2 is that the
download limit is enforced on our server rather than by the storage provider — and that property is
designed in, not added later. Retrofitting it after pre-signed URLs have been emailed to customers
means every link already issued is uncontrolled.

### Phase 5 — Admin operations (6–8 days)
Dashboard, order detail, manual review queue, refunds, customers, downloads admin, coupons, email
events, audit log, payment health widget.
**Done when:** a manually-reviewed order can be fully resolved from the admin without touching a
terminal.

### Phase 6 — Email (3–4 days)
SMTP settings UI with test send, all templates, deliverability DNS checks, `email_events`.
**Done when:** every template renders correctly in the four target clients and passes SPF/DKIM/DMARC.

### Phase 7 — SEO (5–7 days)
Metadata generation and overrides, JSON-LD, sitemaps, robots, redirects, internal linking,
indexability rules, Search Console / Bing registration.
**Done when:** §21.5 passes and Search Console reports no errors on the submitted sitemaps.

### Phase 8 — Hardening (4–6 days)
CSP (report-only, then enforce), all rate limits, 2FA enforcement, upload hardening, authorisation
audit, dependency audit, penetration pass against the §21.3 list, backup encryption and a tested
restore.
**Done when:** §21.3 passes and a restore drill has been completed and timed.

### Phase 9 — Launch readiness (3–5 days)
Load test, CDN tuning, query profiling and index review, monitoring and alerts, staging rehearsal
with live-mode credentials on a test product, runbook.
**Done when:** a real £1 purchase completes in production and the runbook is written.

**Total: roughly 13–18 weeks for one developer**, including the +10–12 days of bilingual work
(§4.7.7) distributed across Phases 1, 2, 5, 6 and 7, plus Phases 2b and 2c. Phases 0–4 (~8–9 weeks)
constitute a sellable store; 5–9 make it operable, discoverable and defensible.

Search and accessibility are **separate numbered phases with their own acceptance criteria**, not
line items inside "storefront". Both were stated as priorities, and work folded into a larger phase
is work that gets cut when that phase runs late.

Bilingual work is **not** a phase of its own, deliberately. Building English first and adding
Spanish afterwards means re-slugging a live catalog, re-registering sitemaps and absorbing a ranking
dip. Both locales are built together, in every phase that produces customer-facing text.

### 23.1 Suggested reduction if time is short

Ship Phases 0–4 plus the dashboard and order detail from Phase 5, and the order-confirmation and
download emails from Phase 6. Defer coupons, attribute landing pages, bundles and the image sitemap.

**Search (2b) can launch reduced**, not skipped: MySQL FULLTEXT behind the same interface, with
Meilisearch swapped in later. A store with no search at all is unusable at any catalog size past
about thirty pieces.

**Accessibility (2c) does not get reduced.** It is cheap while the components are being written and
expensive once the whole site is built on inaccessible patterns — the contrast tokens and the card
link structure in particular are near-impossible to retrofit without redoing the design system.

Do **not** defer: webhook idempotency, amount verification, private storage, 2FA, or backups. Those
are not features; they are the reasons the store does not lose money or data.

## 24. Risks and open decisions

### 24.1 Risks

| Risk | Impact | Mitigation |
|---|---|---|
| Webhook not delivered (site unreachable, config drift) | Orders stick at `pending`; customers pay and receive nothing | Capture response is the primary path; `ReconcileStuckOrders` actively queries PayPal; health check alerts |
| Artwork copied from preview images | Lost sales | Resolution cap + watermark (§10); accept that no technical measure is complete |
| PayPal account limitation | Revenue stops entirely | Keep the payment provider behind an interface so a second provider can be added in days; keep the business documentation PayPal asks for ready |
| `APP_KEY` lost | All customer data unrecoverable | Key stored in a password manager and in the deployment secret store, never only on the server |
| Chargebacks / friendly fraud on digital goods | Fee + lost product | Log IP hash, timestamps and download activity per order; PayPal Seller Protection does not cover digital goods, so evidence matters |
| **PayPal account limitation or fund hold** | **Funds inaccessible; both stores stop** | The highest-probability operational risk at this scale — see §24.3 |
| Shared PayPal account across two stores | A dispute problem in one store limits funds for both | Separate REST apps per store (§6.11); separate business accounts if risk profiles diverge |
| AI-generated work challenged on copyright or platform-policy grounds | Takedown, or inability to enforce the licence sold | Disclose AI generation openly (§7.7, legal draft); sell a **licence to use the files**, never a transfer of copyright |
| libvips unavailable on the host | None — GD measured sufficient (§10.2.1) | GD handles WebP and AVIF at ~3 s per product. Risk downgraded from the original plan. |
| PHP `memory_limit` too low for image processing | First upload of a large original crashes | 512 M required on queue workers; the setup wizard system check asserts it (§3.3) |
| Single server failure | Total outage | Documented 4-hour RTO; infrastructure as code so a rebuild is scripted, not improvised |

### 24.2 Decisions to confirm before Phase 0

1. **Currency** — USD only at launch, or multi-currency? Multi-currency affects the schema
   (per-currency price rows) and is far cheaper to decide now than to retrofit.
2. **Tax/VAT** — EU VAT on digital goods to consumers is legally owed at the buyer's rate from the
   first sale. Options: (a) sell only to one region at launch, (b) integrate a tax service in
   Phase 3, (c) use a merchant of record. **This is the single largest open question in the plan**
   and it is a legal one, not a technical one.
3. **Customer accounts** — guest-only (assumed here) or optional accounts with a purchase library?
4. **Payment methods** — PayPal only, or add Stripe later? If later, the provider interface should
   be introduced in Phase 3 rather than extracted afterwards.
5. **Domain and hosting** — needed before webhook provisioning can be tested.
6. **Brand assets** — logo, fonts, watermark mark; needed before Phase 2.
7. **Country of establishment** — still unconfirmed (LatAm, exact country TBD). It determines PayPal
   withdrawal options and local tax treatment. Blocks §24.3, not the build.

### 24.3 PayPal account risk — the most likely thing to actually go wrong

At this volume, the realistic operational threat is not a tax authority. It is losing access to the
PayPal balance.

Digital goods are a category PayPal treats as elevated risk: no shipping tracking exists to prove
delivery, chargeback rates run high, and Seller Protection does not apply. New sellers, sudden
volume increases and AI-related products all raise review probability further.

**Consequences if it happens:** funds held 21–180 days, a rolling reserve imposed on future sales,
or the account limited outright. Because both stores share one account (§6.11), both stop earning.

**Mitigations, in order of value:**

| Mitigation | Effort |
|---|---|
| Keep delivery evidence per order — acceptance record, delivery timestamp, download logs (already built: §4.3, §7.7.2) | Already in scope |
| Withdraw to a bank account regularly rather than accumulating a balance | Operational habit |
| Respond to every dispute within PayPal's window, with the evidence above attached | Operational habit |
| Keep business documentation ready before PayPal asks: identity, address proof, supplier/process description | One afternoon |
| Have a second provider **ready to enable**, not merely possible — the §6.0 interface makes this a config change once a second adapter exists | ~1 week, deferrable |
| Keep the two stores' order-number prefixes distinct so a dispute is traceable to its source (§6.11) | Already in scope |

**Specific to Latin America:** PayPal's withdrawal mechanics vary enormously by country — some allow
direct local bank transfer, others only permit withdrawal in USD with a poor conversion spread, and
some restrict it substantially. **This must be verified for the specific country before launch**,
because a store that cannot move its revenue into a usable account has a problem no amount of
conversion optimisation solves. It is the one open item that could change the payment provider
decision entirely.

### 24.4 Decision record — taxes deferred

**Decision.** No tax calculation or collection at launch (§7.8).

**Date.** 2026-10-06. **Revisit at** ~$1,000/month revenue, or EU/UK above ~25% of orders, or on
formal business registration.

**Context.** Selling digital goods worldwide from Latin America at roughly $100/month.

**The actual obligation.** EU VAT on digital goods to consumers is owed at the buyer's rate from the
first sale, with **no minimum threshold** for sellers established outside the EU. The UK applies the
same. US state obligations generally require economic nexus (commonly $100k or 200 transactions per
state) and are unlikely to apply at this volume. The existing WooCommerce store is in the same
position: WooCommerce ships with tax calculation disabled and empty rate tables, so an untouched
installation collects nothing. That is the absence of configuration, not compliance.

**Why defer.** Annual exposure is in the low tens of dollars. The alternative — a merchant of record —
costs about 2% more in fees (trivial) but introduces **payout cycles and minimum payout thresholds**
that, at $100/month, can leave revenue trapped for a month or more. That is a concrete cash-flow
problem traded for a small, slow-accruing legal one.

**Accepted risk.** Exposure accumulates retroactively, and regularising it later costs more than
charging correctly from the start. This is accepted knowingly, at this volume only.

**What makes reversal cheap.** The `PaymentProvider` interface (§6.0), the `tax_cents` column that
already exists and flows through every total, and `customers.country` captured from day one so
exposure can be measured rather than guessed when the question is reopened.

**Not legal advice.** This records an engineering decision and its rationale. The position should be
confirmed with an accountant in the country of establishment once that is settled.
